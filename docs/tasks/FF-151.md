# FF-151 Roll folders named by number and ID

**Status:** done · **Built in:** Roll numbers

## Why

Rolls are renumbered freely before their negatives are filed (FF-106, FF-108), often several at once and swapping numbers. A roll's folder named only by its number would clash with another's during a swap (2026-014 ↔ 2026-015). Naming every roll's folder by its number and its ID keeps names unique while they're renamed, and still says the number in Finder.

## What

Every roll's folder is `rolls/YYYY/YYYY-NNN-<ID>/`, its number and the last 8 characters of its ULID, hyphenated (e.g. `rolls/2026/2026-014-Q2P7RM4K/`), filed or not, and the roll repository renames it whenever a save changes the roll's number (D66). A roll is found by the `roll.json` in its folder, never by the folder's name; the paths in `roll.json` are inside the roll's folder, so renaming it changes nothing in the file. FF-106 and FF-108 add the ways to change a number, and use this renaming. *(Replaces D10's rule that a roll's folder is its number alone.)*

## Acceptance criteria

Naming and finding:

- [x] A new roll's folder is `Library/rolls/<year of its number>/<number>-<last 8 characters of its ID>/`, e.g. `rolls/2026/2026-014-Q2P7RM4K/`, with its `roll.json`, `frames/` and `.state.json` in it as now.
- [x] Rolls are found by the `roll.json` in their folder, whatever the folder is called: `2026-014-Q2P7RM4K`, `2026-014` (made before this task), or a name that no longer matches the number (an interrupted rename).
- [x] Rolls already in folders named by number alone stay where they are and keep working until their number changes.
- [x] Adding a version, deleting a frame or version, and deleting a roll find the roll's folder by its ID, wherever it is and whatever it's called.

Renaming:

- [x] Saving a roll with a different number renames its folder to `<new number>-<ID>`, moving it to the new number's year folder if the year changed; an old-style folder is renamed the same way. (Done by `saveRenumbered`, added in FF-106: `save` and `change` no longer change a number.)
- [x] Two rolls swapping numbers are both renamed without either name clashing (by two saves, as FF-151 built it; FF-106 makes the repository refuse a number another roll has, so its swap test then uses a spare number).
- [x] A year folder left empty, by a roll moving out or being deleted, is removed; a year folder with anything in it never is.
- [x] Adding a version to a roll while its number changes never loses the file or puts it in the wrong folder: uploads to a roll and renames of it take turns (they already did: an upload runs inside the roll's `change`, which holds its lock).
- [x] Nothing the API returns, and nothing the UI shows, changes; no response gives a folder or path.

## What was built

**Naming and finding.** `roll-folder.ts` has `rollFolderFor` (`rolls/YYYY/YYYY-NNN-<ID>/`) and `findRollFolder`, which looks first for a folder whose name ends in the roll's ID and checks the `roll.json` in it says it's the roll's, then any folder whose `roll.json` does (so folders named by number alone, or left by an interrupted rename, are found). The blob store's `put` and `get` and the new `NewBlob.rollId` take the roll's ID instead of its number; the use cases (`AddVersion`, `GetOriginal`, `GetThumbnail`) pass `roll.id`. The holding area finds the roll's folder by `held.rollId`, holds a roll's folder under its own name (`deleted/…-roll-<ID>/2026-014-Q2P7RM4K/`), and, as before, has nothing to move for a frame or version whose roll has no folder.

**Renaming.** `FilesystemRollRepository` makes new rolls' folders with the number-and-ID name, checks the number is free (an unreadable roll's folder named for it counts) and makes the folder under one lock so two new rolls can't take a number, and renames a roll's folder when a save (`save` or `change`) changes its number: the folder first, to another year's folder if need be, then `roll.json` in it. An existing target refuses the rename, changing nothing. A year folder left empty, by a rename or by `remove`, is removed; one with anything in it never is. Year folders are made and removed under one lock.

**Tests.** The filesystem roll repository tests cover the naming, old-style and oddly named folders, a lookalike folder, renaming (same year, new year, old-style folders, swaps, an interrupted rename, a refused rename, `change`), and year folders; the blob store and holding area contract suites take a `createRoll` step; `roll-folders-together.test.ts` adds a version while a roll is renumbered; the API tests find roll folders with `folderOfRoll`. The journeys ran unchanged. Nothing in the UI or API changed, and numbers can't yet be changed through the API (FF-106), so the renaming is exercised by the repository tests.

## Not in this task

- Ways to change a roll's number: by hand (FF-106) and Number rolls (FF-108).
- Frame and version folders named by number and kind (FF-155).
- Recovering a folder whose rename was cut short (FF-156).
- Moving existing rolls into the new naming before their number changes.

- A rename changes the folder's path, so backup and sync see its files as new, and links into it are rebuilt (the NegPy folder, FF-112); renumbering mostly happens while a roll holds only the lab's small scans.
