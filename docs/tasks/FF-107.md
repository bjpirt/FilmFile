# FF-107 Mark a roll as filed

**Status:** done · **Built in:** 2. Roll numbers · **Was:** U92

## Why

Once a roll's negatives are in the physical archive with its number on the sleeve, the catalogue must never move that number, or the shelf and the catalogue disagree.

## What

"Mark as filed" in a roll's Actions menu fixes its number. A padlock marks it after the roll number on its card in the rolls view and in the roll page heading; in Edit details, the number stays visible but can't be changed. "Unmark as filed…" is available when it needs correcting.

## Acceptance criteria

- [x] "Mark as filed" in Actions marks the roll immediately, using the loaded ETag. Its number and folder stay the same; `roll.json` gains `filed: true`.
- [x] A filed roll shows a padlock named and titled "Filed" after its number in the roll page heading.
- [x] A filed roll's card in the rolls view shows a "Filed" padlock after its number. Individual frames, list rows, event pages and the filmstrip do not show it.
- [x] In Edit details, a filed roll's number is visible as non-editable text, followed by the "Filed" padlock, with "Filed: unmark it to change the number."
- [x] "Unmark as filed…" opens an in-page confirmation with "Only unmark it if its negatives aren't filed under this number.", and "Unmark as filed" and "Cancel" buttons. Confirming removes `filed` from `roll.json`; it does not rename the folder.
- [x] Marking or unmarking a roll changed elsewhere since the page loaded is refused with 409; the page says "The roll changed since you opened it. Reload the page." and changes nothing.
- [x] The manual `PATCH /api/rolls/{rollId}` refuses a request to change an already-filed roll's number with 422 and "A filed roll's number can't be changed." A stale ETag remains a 409. Batch renumbering is in FF-108.
- [x] The roll API always returns `filed` as a boolean; `PATCH /api/rolls/{rollId}` accepts an optional boolean `filed` to mark or unmark the roll.
- [x] `roll.json` writes `filed: true` only when set; an absent field, including in an older file, means unfiled.

## What was built

- `PATCH /api/rolls/{rollId}` accepts `filed`; responses always include the boolean. The repositories preserve the version check and refuse a filed roll's number change with 422.
- The filesystem schema defaults missing `filed` to false and omits it when false, keeping old unfiled files unchanged.
- The roll page has the immediate "Mark as filed" action, confirmed "Unmark as filed…" action, a heading padlock, and a read-only filed number with a padlock in Edit details. Filed roll cards show a padlock after their number; frame thumbnails do not.
- Backend repository, persistence, API and use-case tests, plus roll-page and rolls-view tests, cover the filed state and its constraints.

## Not in this task

- Where a roll is filed (box, binder, page): not recorded or tracked for now.

## Notes

- Decisions D66 (folder names), D74 (filed numbers never change), D71 (stored and API representation and error status), and D72 (padlock and confirmation).
- A missing `filed` field defaults to `false` in the domain model; adding this optional field needs no migration. Saving `false` removes the field so unchanged unfiled rolls remain byte-identical.
- Filing changes only `roll.json`; it never renames the roll folder (D66). Deleting a filed roll remains allowed after the existing confirmation (D38).
- Tests: repository and API tests for marking, unmarking, defaulting old files, ETags, unchanged folder names, and refused number changes; roll-page tests for the actions, cancellation, Edit details padlock and conflict; rolls-view tests for the card padlock and its absence in list view. The FF-108 journey already covers filing a roll, so this task adds no journey.
