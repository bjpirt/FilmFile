# FF-195 Make a release

**Status:** to do · **Group:** 10. Desktop app

## Why

Releasing a new FilmFile in one step: a version number, a changelog, and the app for every platform, built and checked the same way each time, rather than by hand on my Mac.

## What

A "Release" workflow, started by hand on GitHub on `main`, with a choice of patch, minor or major. It works out the next version from the last tag, builds and checks the app on every platform through `package.yml`, and only if they all pass:

1. It commits the new version and a `CHANGELOG.md` entry written from the commits.
2. It tags that commit.
3. It publishes a GitHub release with the apps and their checksums.

At first that's the two Mac disk images. Windows and Linux join when they're built (FF-197, FF-198).

## Acceptance criteria

- [ ] Actions › "Release" › "Run workflow" offers "patch", "minor" and "major" (default "patch"), and runs only on `main`.
- [ ] The next version comes from the latest `v*` tag. With no tag yet, the first release is the root `package.json`'s `0.1.0` as it is, whichever choice is made. After that: from `v0.3.2`, patch gives `0.3.3`, minor `0.4.0` and major `1.0.0`. A unit test covers the rule.
- [ ] It builds and runs the packaged-app journey on every platform in `package.yml`, with the new version. If any of them fails, nothing is committed, tagged or released.
- [ ] Once they all pass, one commit on `main`, "chore: release 0.4.0", sets the version in the root `package.json` (the only one that holds it, FF-194) and adds the entry at the top of `CHANGELOG.md`. It's tagged `v0.4.0`.
- [ ] The changelog entry is headed "## 0.4.0 (2026-11-20)". Under it come "### Added" (the `feat:` commits) and "### Fixed" (the `fix:` commits) since the last tag, one line each, with the commit's subject and short hash. Other commits are left out. A heading with nothing under it is left out. A unit test covers the entry.
- [ ] The GitHub release "FilmFile 0.4.0" is published at once (not a draft), its notes the changelog entry. It holds every platform's file and `SHA256SUMS`, one line per file in `sha256sum`'s format, checkable with `shasum -a 256 -c SHA256SUMS`.
- [ ] Only one release runs at a time (a concurrency group), and a release of a commit already tagged is refused.
- [ ] Only the last job, which commits, tags and releases, can write (`contents: write`). The build jobs read only, and no other secret is used. Actions are pinned to commit SHAs.

## Not in this task

- Signing (FF-137, FF-199) and updates (FF-138). Until then, macOS asks before opening a downloaded app (System Settings › Privacy & Security › Open Anyway), and so will Windows SmartScreen.
- Running `pnpm verify` and the browser journeys again: `main`'s CI already has (the release checks only the packaged apps).
- Pre-releases, and releasing from another branch.

## Notes

- D109: version from tags, bumped by the Release workflow, which commits the version and changelog to `main` (no branch protection; revisit if `main` is protected, with a release PR instead).
- The version and changelog are worked out by a small script of our own (`scripts/release.ts`, Node, no dependency) from `git tag` and `git log`, unit tested.
- The commit is made with `GITHUB_TOKEN`, so it doesn't start CI again. Its contents were built and checked by the release itself.
- Files are named `FilmFile-<version>-<platform>-<arch>.<ext>` (FF-194).
- Check against `security-rules` for CI. Tests: the version and changelog script (unit). The workflow is tried by making `v0.1.0`.
