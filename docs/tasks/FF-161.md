# FF-161 An Intel Mac build

**Status:** to do · **Group:** 10. Desktop app

## Why

Running FilmFile on an Intel Mac as well as on Apple silicon.

## What

`pnpm package` builds for the Mac it runs on, Apple silicon or Intel, and CI builds and checks both, each on its own runner. CI's `desktop-app` job becomes a reusable workflow, `package.yml`, with one row per platform. The Release workflow (FF-195) uses it, and Windows and Linux add their rows later (FF-197, FF-198).

## Acceptance criteria

- [ ] On an Intel Mac, `pnpm package` makes `FilmFile-<version>-mac-x64.dmg`. On Apple silicon it makes `FilmFile-<version>-mac-arm64.dmg`, as now.
- [ ] Each architecture's app holds sharp's native files for that architecture only.
- [ ] `.github/workflows/package.yml` (`workflow_call`) builds the app and runs the packaged-app journey on `macos-latest` (Apple silicon) and `macos-15-intel` (Intel), then uploads each disk image as a build artifact for 7 days.
- [ ] `ci.yml` calls it in place of the `desktop-app` job, on every push to `main` and every pull request.
- [ ] The packaged-app journey finds the app for the platform and architecture it runs on, and is skipped, as now, when it isn't built.
- [ ] `package.yml` keeps CI's rules: actions pinned to commit SHAs, `contents: read`, `--frozen-lockfile`, no secrets.

## Not in this task

- Releases (FF-195). A universal app holding both architectures: two disk images are about half the download each.
- Windows and Linux (FF-197, FF-198).

## Notes

- Each architecture is built on its own runner, because pnpm installs sharp's native files only for the machine it runs on, and `package.ts` copies what's installed (D110).
- `macos-15-intel` is GitHub's last Intel image. When it's retired, Intel builds move to the Apple silicon runner, with pnpm's `supportedArchitectures` installing x64 sharp and the journey run under Rosetta.
- `package.ts` takes the platform and architecture from `process.platform` and `process.arch`.
