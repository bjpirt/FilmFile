# FF-243 Prepare a release

**Status:** done · **Built in:** 10. Desktop app

## Why

Starting a release in one command: the next version and its changelog worked out for me, in a pull request I can read and correct before anything is published.

## What

`pnpm release patch` (or `minor`, `major`), run on an up-to-date `main`, works out the next version from the root `package.json`, sets it there, adds an entry to `CHANGELOG.md` from the commits since the last release, and opens a pull request "chore: release 0.4.0", labelled "release", on a branch of its own, then goes back to `main`. Merging it publishes the release (FF-244); until then, the notes can be corrected in the pull request. `--dry-run` shows what it would do and changes nothing. _(Split from FF-195.)_

## Acceptance criteria

The version:

- [x] `pnpm release patch`, `minor` or `major` works out the next version from the root `package.json`: from `0.3.2`, patch gives `0.3.3`, minor `0.4.0` and major `1.0.0`. A unit test covers the rule.
- [x] `pnpm release` with no choice, or another word, changes nothing and says: "Say which: pnpm release patch (0.3.3), minor (0.4.0) or major (1.0.0)."
- [x] Before any release has been made (no `v*` tag), the version is kept as it is: the first release is `0.1.0`, whichever is chosen.
- [x] It sets the version in the root `package.json` only (FF-194), and adds the entry at the top of `CHANGELOG.md`, which it makes if there isn't one.

The changelog entry (unit tested):

- [x] It's headed "## 0.4.0", with no date (the release shows when it was published).
- [x] Under it come "### Changed" (breaking changes: `feat!:`, `fix!:` or a `BREAKING CHANGE:` footer), then "### Added" (`feat:`) and "### Fixed" (`fix:`), from the commits since the last `v*` tag. Other commits are left out, and so is a heading with nothing under it. Choosing patch with breaking changes is allowed.
- [x] Each line is the commit's subject without its prefix (and scope, as in `feat(sync):`), its first letter capitalised, then its short hash linked to the commit on GitHub: "- The app's version, in Settings and About, with a link to GitHub (FF-194, D124) ([293fe7f](https://github.com/bjpirt/FilmFile/commit/293fe7f))".
- [x] With no `feat:` or `fix:` commits since the last release, the entry says "Maintenance: dependencies and tidying."
- [x] The first release's entry says "The first release."

The pull request:

- [x] It commits both, as "chore: release 0.4.0", on a new branch `release/0.4.0`, pushes it, and opens a pull request with that title and the label "release" (made if the repository hasn't one). It doesn't turn on auto-merge: merging is what publishes.
- [x] The pull request's description is the entry, then: "Merging this publishes FilmFile 0.4.0. Edit CHANGELOG.md in this pull request to change the notes."
- [x] It prints the pull request's link, and leaves me on `main`.
- [x] `pnpm release minor --dry-run` prints the version, the branch and the entry ("Would release 0.4.0 on release/0.4.0:"), and changes nothing: no file, branch, commit, push or pull request.

When it refuses (each before changing anything, saying why):

- [x] Not on `main`: "Run it on main."
- [x] Uncommitted changes: "Commit or put away your changes first."
- [x] `main` differs from GitHub's after fetching: "main is 2 commits behind GitHub's. Run git pull first." or "main has 1 commit GitHub doesn't. Push it in a pull request first."
- [x] The version in `package.json` hasn't been released yet (no tag for it) but an earlier one has: "0.4.0 hasn't been published yet. Run the Release workflow on main to publish it."
- [x] A pull request labelled "release" is already open: "A release is already open: `https://github.com/bjpirt/FilmFile/pull/42`. Merge or close it first." (with its link)
- [x] `release/0.4.0` already exists, here or on GitHub.
- [x] `gh` isn't installed or signed in: "GitHub's gh isn't signed in. Run gh auth login, then try again." (or says to install it).

## What was built

- `pnpm release` runs `scripts/release.ts`. The parts that decide are plain functions in `scripts/release/`, each unit tested: `next-version.ts`, `parse-commits.ts` (reads `git log --format=%h%x1f%s%x1f%b%x1e`), `changelog-entry.ts`, `with-entry.ts`, `release-refusal.ts` (every refusal, in the order above, after the gh check), `release-usage.ts` and `release-description.ts`.
- `scripts/release.ts` fetches `main` and the tags, gathers the facts and refuses before changing anything; then it makes `release/<version>`, writes `package.json` and `CHANGELOG.md`, commits, pushes, makes or updates the "release" label (`gh label create release --force`), opens the pull request with `gh pr create --body-file -`, and switches back to `main`. A dry run does the same checks, so it says whether the real run would work.
- `scripts/release.test.ts` runs it for real against a throwaway repository and a bare one standing in for GitHub, with a fake `gh` that keeps its calls: a full release, the first release, a dry run, no choice, and four refusals.
- `scripts/` is in the root `tsconfig.json`, so it's typechecked and linted. The README says how to release.
- Merging the first release changes only `CHANGELOG.md` (0.1.0 is kept), so FF-244's workflow also starts on a change to it.

## Not in this task

- Publishing the release when the pull request is merged (FF-244).
- Preparing a release from GitHub's Actions tab (FF-245).
- Running `pnpm verify` first: the commit hook runs its checks, and CI runs everything on the pull request.
- Pre-releases, and releases from another branch.
