# FF-150 Settings for the whole FilmFile folder

**Status:** done · **Built in:** The FilmFile folder

## Why

The archive's author and copyright were kept in the library, but what's coming (export recipes, event site defaults, the S3 bucket) is about the whole FilmFile folder, not the library. One settings file and one API for everything FilmFile-wide, with the folder's own path shown in Settings.

## What

`archive.json` moves up out of `Library/` to the FilmFile folder's top level and becomes `settings.json` (D65), and the API's `/api/archive` becomes `/api/settings`, in the same way, with a read-only `folder` field giving the FilmFile folder's path, which Settings shows (D64). *(Split from FF-105.)*

## Acceptance criteria

The file:

- [x] `settings.json` sits in the FilmFile folder, beside `Library/`, and holds what `archive.json` did: `schema`, `id` and `meta` (the author and copyright). `Library/` no longer has an `archive.json`.
- [x] `settings.json` doesn't hold the folder's path.
- [x] Saves need the expected version token, are atomic and keep a stable key order, as for every file the service writes.
- [x] A folder with a `Library/` but no `settings.json` is a FilmFile folder not yet set up, as an empty one is (FF-105).

The API:

- [x] `GET`, `POST` and `PATCH` `/api/settings` do what `/api/archive` did: `GET` is 404 until it's set up, `POST` sets it up once (409 when it already is), `PATCH` changes the author and copyright with `If-Match` (428 when missing, 409 when stale); `/api/archive` is gone.
- [x] The response has the author and copyright, and a read-only `folder`: the FilmFile folder's absolute path, from the service's own settings, the only absolute path any response carries (D64).
- [x] `PATCH` and `POST` take no folder: one sent changes nothing.
- [x] The OpenAPI spec and the generated client have the new routes and schema names (`Settings`), and no mention of the archive's details.

The web UI:

- [x] First run asks "Set up FilmFile" (replacing "Set up your archive") for the author and copyright, with the copyright made from the author as now, and the button "Set up".
- [x] Settings shows, under the form, "FilmFile folder", its path as text that can be selected and copied, and "Change it in the app with File › Open FilmFile Folder…, or set FILMFILE_FOLDER and restart."
- [x] Saving Settings still goes back to the rolls page.

Everything else:

- [x] A frame's author and copyright still resolve from the settings, with where they came from (the archive layer, as now), and the roll and frame views show the same as before.
- [x] Port, adapters, use cases and web files are named for settings (`SettingsRepository`, `GetSettings`, `use-settings`), with no file left from `archive`'s details.
- [x] The first-run journey, the desktop journeys and the browser journeys pass with the new heading and routes, and the first-run journey also finds the folder's path in Settings.

## What was built

**The file and port.** `settings.json` is written at the FilmFile folder's top level by `FilesystemSettingsRepository` (`settings-file.ts` for its format, unchanged from archive.json's: `schema`, `id`, `meta`), and an empty `Library/` has nothing in it. The domain type is `Settings`, the port `SettingsRepository` (`VersionedSettings`), and the use cases `GetSettings`, `InitialiseSettings` and `UpdateSettings`, with the entity named `settings` in errors. The resolver's layer is still `archive`.

**The API.** `/api/settings` (`routes/settings.ts`; contracts `settings.ts`, schema ids `Settings`, `CreateSettingsRequest`, `UpdateSettingsRequest`) does what `/api/archive` did. Each answer has `folder`, added by the route from the service's own `folderPath`, so the file never holds it and nothing sent can set it (the request schemas have no folder, so one sent is ignored). `createApp` and `composeLocal` take `folderPath` (`composeInMemory` uses `/in-memory/FilmFile`). `pnpm generate` rewrote the OpenAPI spec and client.

**The web UI.** `apps/web/src/settings/` (`use-settings.ts`, `settings-form.tsx`, `set-up-page.tsx`, `settings-page.tsx`). First run says "Set up FilmFile" (form and heading) with the button "Set up"; Settings shows, under the form, a "FilmFile folder" heading, the path as selectable text, and "Change it in the app with File › Open FilmFile Folder…, or set FILMFILE_FOLDER and restart." The web tests' fake service answers `/api/settings` the same way.

**Tests.** The API test covers the new route, `settings.json` at the folder's top level (and the Library left empty), the `folder` field, and no folder taken from a request; the repository contract suite runs against the memory and filesystem adapters; page tests cover first run and Settings; the first-run journey checks the folder on Settings; the desktop and packaged journeys use the settings file. The test folder helper (`useTempArchive`) now makes a FilmFile folder with its `Library/` (`.folder()` and `.path()`).

## Not in this task

- Changing the folder from Settings (FF-105's "Not in this task").
- Per-computer values such as an AWS profile: they stay out of this file, which is synced between devices (D52); FF-121 decides where they go.
- New settings (export recipes, site options, the S3 bucket): each is added by its own task.
- Renaming the resolver's archive layer, or "archive" meaning the library elsewhere in the code and UI.
- Moving or converting an existing `archive.json`: nobody is using one yet.
