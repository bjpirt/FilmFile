# FF-159 Custom roll number pattern

**Status:** done · **Built in:** 7. Roll numbering and filing

## Why

I can have FilmFile suggest roll numbers in the format I use, both when creating rolls and when putting unfiled rolls in order.

## What

Add a separate “Roll number pattern” section to Settings. The archive-wide pattern is saved in `settings.json` and previews a rendered example. Use it for the roll-number suggestion on New roll and for proposed numbers in “Re-number rolls…”. It depends on FF-153's freeform roll-number support.

## Acceptance criteria

- [x] Settings has a “Roll number pattern” section with its own Save action, separate from author/copyright. Saving keeps the user on Settings and shows the saved pattern and preview.
- [x] The default pattern is `{year}-{n:3}`. A settings file without a saved pattern uses this default.
- [x] A pattern is fixed text, one sequence token with a minimum digit width of 1 to 9 (`{n:3}`), and optional `{year}`, `{month}`, `{day}` and `{event}` tokens. Fixed text is anything except `{` and `}`. Month and day render as two digits; `{event}` renders the roll's event slug. Examples include `{year}-{n:3}`, `{n:4}`, `BP-{year}-{n:2}`, `{year}{month}-{n:3}` and `{event}-{n:2}`.
- [x] The Settings section previews the pattern with an example shot date and sequence value. Invalid syntax, missing or repeated sequence tokens, unknown tokens, or a generated label longer than FF-153's 100-character limit is refused with a clear message and changes nothing.
- [x] The pattern is stored in `settings.json` and exposed through the Settings API. Updating it uses the settings version token; a stale save says “The settings changed since you opened them. Reload the page.” Old settings without the field still load as the default.
- [x] A New roll opens with a suggested number rendered from the current pattern and shot date. The suggestion updates when the date changes until the user types over the number. If the pattern uses `{month}` or `{day}`, the form requires those date parts.
- [x] Saving a pattern that uses `{month}`, `{day}` or `{event}` is refused until every existing roll has the required shot-date precision or an event. *(Creating and editing a roll don't refuse a missing month, day or event: D89, FF-154.)*
- [x] The sequence advances after the highest existing matching value in its token group, never reuses gaps, and skips occupied labels. Its width is a minimum and generated numbers can grow past 999. Counters reset for the distinct date-token and event values present; labels that don't match the current pattern never set a counter or anchor, though every existing label stays occupied; without date tokens, one counter runs across the archive.
- [x] “Re-number rolls…” proposes labels from the pattern, grouping by the pattern's date-token and event values. A matching unfiled roll with no shot date still blocks numbering, as in FF-108. It retains FF-108's shot-date order, filed-roll anchors, active Browse filter scope, and filtered-out occupied labels; without date tokens, numbering uses one global group. Pattern changes alone do not renumber existing rolls.
- [x] A `POST /api/rolls` request that omits `roll` keeps the existing service-generated default; this pattern changes UI suggestions only. The New roll page sends its suggested value, and “Re-number rolls…” sends its previewed values.
- [x] Tests cover settings persistence and legacy defaults, pattern parsing and previews, missing date precision, new-roll suggestions, collisions, and custom-pattern “Re-number rolls…” previews and saves.

## What was built

Settings has a separate “Roll number pattern” form (its own Save, staying on Settings) with a live example. The pattern is `rollNumberPattern` at the top level of `settings.json`, left out while it is the default, exposed on `GET`/`PATCH /api/settings` and saved with the settings' version token. Backend `domain/settings/roll-number-pattern.ts` parses the pattern and its needs; `UpdateSettings` refuses an invalid pattern or one a roll can't meet, and `CreateRoll` and `UpdateRoll` keep a roll's shot date and event as the pattern needs. The web's `rolls/roll-number-pattern.ts` renders, reads and suggests numbers; New roll suggests from it (waiting for a new event's slug when the pattern uses `{event}`), and “Re-number rolls…” (`numbering-preview.ts`) groups by the pattern's date and event values. The “Re-number rolls…” request now accepts any roll number, and its 999 limit is gone. An API create with no number still uses the service's own default, capped at 999.

Tests: pattern parsing and rules (backend and web, kept in agreement), settings file, use cases and API, New roll and Settings pages, and the Re-number rolls… preview and apply.
