# FF-161 An Intel Mac build

**Status:** done · **Built in:** 10. Desktop app

## Why

Running FilmFile on an Intel Mac as well as on Apple silicon, from a release that says plainly which download is mine.

## What

`pnpm package` already builds for the Mac it runs on, Apple silicon or Intel. This adds an Intel row (`macos-15-intel`) to `package.yml` beside Apple silicon's, so every pull request, every push to `main` and every release builds and checks both, and a release (FF-244) publishes both disk images. `package.ts` refuses to make an app holding another architecture's sharp files. The release notes say which disk image is for which Mac. Windows and Linux add their rows later (FF-197, FF-198).

## Acceptance criteria

- [x] On an Intel Mac, `pnpm package` makes `FilmFile-<version>-mac-x64.dmg`. On Apple silicon it makes `FilmFile-<version>-mac-arm64.dmg`, as now.
- [x] `package.ts` checks the app holds sharp's native files (`@img/sharp-darwin-<arch>`, `@img/sharp-libvips-darwin-<arch>`) for its own architecture only, and stops otherwise, saying, for example, "FilmFile.app would hold sharp for arm64 and x64; it should hold only arm64’s."
- [x] `.github/workflows/package.yml` has a row `mac-x64` on `macos-15-intel` beside `mac-arm64` on `macos-latest`. Each builds the app, runs the packaged-app journey and uploads its disk image as `FilmFile-<platform>` for 7 days, on every pull request, every push to `main` and every release.
- [x] One row failing doesn't cancel the other (`fail-fast: false`). A release still publishes nothing unless both pass.
- [x] `desktop-app / mac-x64` is reported on every pull request, ready to be made a required check in the ruleset on `main` beside `desktop-app / mac-arm64`, by hand, once this is merged (required sooner, it would hold up every other open pull request, whose CI has no such check).
- [x] The packaged-app journey finds the app for the architecture it runs on, and is skipped, as now, when it isn't built.
- [x] A release (FF-244) holds both disk images, each in `SHA256SUMS` with its own provenance.
- [x] Its notes' "### Installing" starts: "Download the disk image for your Mac (Apple menu › About This Mac shows its chip):", then "- Apple silicon (M1 or later): FilmFile-0.4.0-mac-arm64.dmg" and "- Intel: FilmFile-0.4.0-mac-x64.dmg", then "Needs macOS 12 Monterey or later." before the note on opening it. A unit test covers the notes.
- [x] `package.yml` keeps CI's rules: actions pinned to commit SHAs, `contents: read`, `--frozen-lockfile`, no secrets, no cache for a release.

## What was built

- `apps/desktop/scripts/sharp-architecture-problem.ts` (unit tested) says what's wrong with the app's `node_modules/@img`; `package.ts` stops with its message after copying sharp. `@img/colour` isn't native, and doesn't count.
- `package.yml`'s matrix has `mac-x64` on `macos-15-intel` beside `mac-arm64`, with `fail-fast: false`. The release workflow already downloads every `FilmFile-*` artifact, so both disk images reach `SHA256SUMS`, provenance and the release.
- `scripts/release/release-notes.ts`: "### Installing" names each Mac's disk image for the version, and says it needs macOS 12 Monterey or later.

## Not in this task

- Releases themselves (FF-243, FF-244).
- A universal app holding both architectures: two disk images are about half the download each.
- Checking `pnpm install:app` on an Intel Mac: it already picks the app for the machine's architecture.
- Windows and Linux (FF-197, FF-198).

## Notes

- Each architecture is built on its own runner, because pnpm installs sharp's native files only for the machine it runs on, and `package.ts` copies what's installed (D110). `package.ts`, `install-app.ts` and the packaged-app journey already go by `process.arch`.
- `macos-15-intel` is GitHub's last Intel image. When it's retired, Intel builds move to the Apple silicon runner, with pnpm's `supportedArchitectures` installing x64 sharp and the journey run under Rosetta.
- macOS 12 is Electron 45's oldest supported macOS.
- The ruleset is changed by hand (Settings › Rules › Main Protection), with this task's pull request.
- The release notes (`scripts/release/release-notes.ts`) gain the version's file names.
