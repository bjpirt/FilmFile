# FF-215 A site's reads and writes in one place

**Status:** to do · **Group:** 16. Internal improvements

## Why

The sites pages call the API client directly from four files, each defining its own query keys and deciding what to refresh. As with rolls (FF-212), one place per feature keeps them agreeing.

## What

`sites/use-site.ts` holds the sites' query keys and reads; `sites/site-changes.ts` holds their writes, each owning its 409 check and what it refreshes. The sites pages use them. Nothing a person sees changes. _(Recommendation R7 of the architecture review, for sites. The review advises doing this when feature work next touches sites, not up front.)_

## Acceptance criteria

- [ ] `apps/web/src/sites/use-site.ts` exports the keys as functions (`sitesKey`, `siteKey(slug)`, `siteStatusKey(slug)`) and `useSites(api)`, `useSite(api, slug)` (with its version, for saving) and `useSiteStatus(api, slug)`, each the one definition of its query.
- [ ] `apps/web/src/sites/site-changes.ts` has one function each for: make a site, save a site, delete a site, start a build and cancel a build. Each returns a small union of outcomes (`'saved' | 'changed-elsewhere' | 'failed'`, or what that write needs, such as a name already taken), and refreshes what it refreshes now.
- [ ] `sites-page.tsx`, `site-page.tsx`, `build-panel.tsx` and `use-site-saver.ts` use them and call the API client no more.
- [ ] `sites-page.test.tsx`, `site-page.test.tsx`, `build-site.test.tsx` and the Playwright journeys pass unchanged.
- [ ] Each new write function has a test for each of its outcomes.

## Not in this task

- Splitting the site page.
- Changing how a build's status is polled.
