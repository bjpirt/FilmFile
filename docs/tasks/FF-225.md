# FF-225 Back up the library to a bucket

**Status:** done · **Built in:** 17. Sync and backup

## Why

A copy of the whole library somewhere other than this computer, made in one click, so a lost or broken disk loses nothing. It's also the first half of syncing between computers.

## What

A "Sync" section in Settings, in the desktop app, takes a Cloudflare R2 bucket in the account set in Settings (FF-236) and this computer's name, both kept by the desktop app for this computer only. "Sync" uploads `Library/` and `settings.json` to the bucket as a mirror of the folder, sending only what's new or changed since the last sync, and records the sync in the bucket. The first sync claims an empty bucket for this library. Until another computer joins (FF-227), syncing only goes up. Renames, removals and files gone missing are the next task (FF-238). _(Split, with FF-238, from the first plan of this task.)_

## Acceptance criteria

- [x] In the desktop app, Settings has a "Sync" section after "Cloudflare", with "Bucket", "This computer's name" and "Save". The name starts as this computer's own name, with any `.local` ending taken off, and can be changed (1–60 characters). Both are kept by the desktop app for this computer only, never in the FilmFile folder.
- [x] Until a Cloudflare account ID is set and a bucket saved, it reads "Say which bucket to sync with." and "Sync" is disabled.
- [x] Without the desktop app (the service on its own), the section reads "Sync works in the FilmFile app." and has no fields.
- [x] A field that isn't valid says why under it, in the service's words, and isn't saved: a bucket name R2 wouldn't take (FF-201's rule), a name that's empty or over 60 characters.
- [x] "Sync" with an empty bucket claims it for this library and uploads every file under `Library/`, plus `settings.json`, at the same paths. Names starting with `.` (such as `.DS_Store`) are never synced.
- [x] While it runs it reads "Uploading 1.2 GB of 34 GB (12 of 340 files)", with "Cancel". When it's done it reads "Synced 16 Nov 2026, 14:02", in this computer's time zone, and what it sent: "Sent 12 files (1.2 GB).", or "Nothing had changed."
- [x] Syncing again uploads only files that are new or have changed since the last sync. With nothing changed it uploads nothing and reads "Synced …" with the new time.
- [x] Files are streamed from disk, four at a time, so memory stays small whatever their size.
- [x] A file edited while a sync runs is never recorded wrongly: the bucket's manifest holds the hash of what was actually sent, and the next sync sends it again if it changed.
- [x] A bucket that isn't empty and wasn't claimed by this library is refused, changing nothing: "That bucket has something else in it, so FilmFile won't sync with it." One claimed by another library: "That bucket belongs to another FilmFile library."
- [x] A sync that fails or is cancelled part-way leaves the bucket's sync record and manifest as they were, keeps what was uploaded, and reads "Sync didn't finish. Nothing already backed up was lost. Try again." The next sync uploads only what's still missing.
- [x] Failures use publishing's words: no account ID, no `[filmfile]` keys, keys refused, no such bucket and offline, with "Open Settings" after those fixed there, and "Couldn't sync." for anything else, with R2's reason written to the service's log.
- [x] The API: `GET`/`PUT /api/sync/settings`, `POST /api/sync` (start, 202), `GET /api/sync` (status and progress), `DELETE /api/sync` (cancel). All are in the OpenAPI spec.
- [x] A journey sets the account ID and a bucket, syncs to the fake R2, sees "Synced …", syncs again and sees "Nothing had changed.", then changes the copyright and syncs again, seeing "Sent 1 file". (The copyright, in `settings.json`, rather than a frame's details: one file whichever it is, and simpler to change.)

## What was built

- **Domain** (`domain/sync/`): `planBackup` and `manifestAfter`, the bucket's `sync.json` and `manifest.json` read and written by hand-written checks (`sync-files.ts`, no Zod in the core), `parseComputerName` and `computerNameFrom`, and `syncFailureMessage`. The bucket-name rule moved to `domain/shared/bucket-name.ts`, shared with publishing.
- **Ports:** `PublishBucket` gained `get`, `putIf` (`If-None-Match: *`, `If-Match`) and `putStream` (sent unsigned with its length, hashed as it goes, its MD5 checked against the ETag); `LibraryFiles` (`FilesystemLibraryFiles`, hashes cached in the cache folder; `InMemoryLibraryFiles`); `SyncSettingsStore` (`ParentProcessSyncSettings`, `FileSyncSettings`, `InMemorySyncSettings`). Each has a contract suite; the fake R2 gained get, conditional put and a required `Content-Length`.
- **Use cases** (`application/use-cases/sync/`): `GetSyncSettings`, `SaveSyncSettings` and `LibrarySync` (`start`, `status`, `cancel`).
- **Routes** (`routes/sync.ts`): `GET`/`PUT /api/sync/settings`, `GET`/`POST`/`DELETE /api/sync`; whether sync is available is the settings' `available`, not the health check.
- **Desktop app:** its settings file keeps `sync`, and it answers `get-sync-settings` and `save-sync-settings`.
- **Page:** `settings/sync-section.tsx` after Cloudflare in Settings, with `format-bytes.ts`.
- **Journey:** `test/e2e/back-up.e2e.ts`, with `serve.ts` setting `FILMFILE_SYNC_SETTINGS` and a backup bucket in the fake R2. `docs/publishing-to-cloudflare.md` gained "Backing up the library".
- Not tried against real Cloudflare: streamed uploads and conditional puts have only met the fake R2.

## Notes

- **Decisions:** D115, D117, D118, D119, and D120 (sync's settings in the desktop app, the manifest from the bucket, hashes cached, dotfiles skipped).
- **Per computer (D120):** the bucket, this computer's name and the last sync number are kept by the desktop app with its other per-computer settings (the FilmFile folder), and the service reads and saves them over its private channel to the app, as it asks for an export folder (D100). `GET /api/health` (or the settings) says whether sync is available, as `exportToFolder` does. For tests only, `FILMFILE_SYNC_SETTINGS` names a JSON file the service uses instead, read only from the environment.
- **Bucket layout (D117):** the bucket mirrors the folder (`Library/…`, `settings.json`). `filmfile/sync.json` (archive ID, sync number, computer name and time) and `filmfile/manifest.json` (every file's path, size and SHA-256) are written last, conditionally on the record read at the start, so a sync cut short leaves the old record in force.
- **Comparing:** each sync downloads the bucket's `manifest.json` (the last sync's) and compares the library with it. SHA-256s are cached by path, size and modified time in the OS cache folder; a cleared cache only means hashing again. The manifest records the hash of the bytes actually streamed.
- **Order of a push:** files, then the manifest and the sync record.
- **Requests:** FF-201's signing and `[filmfile]` keys, the R2 adapter extended: get (the record and manifest), conditional put (`If-None-Match: *` to claim, `If-Match` for the record), and put streamed from a file with its known SHA-256 as the payload hash. One PUT holds up to 5 GB, so no multi-part uploads. The contract suite runs against the in-memory adapter and the fake R2, which gains get and conditional put.
- **Security** (the `security-rules` skill): requests only to the account's R2 host, bucket keys built from library-relative paths, local paths through the safe-path helper, and a downloaded record and manifest parsed with Zod.
- **The guide:** `docs/publishing-to-cloudflare.md` gains backing up: a bucket of its own, covered by the token.
- **Tests:** unit (planning uploads from the library and the last manifest; the hash cache), contract (bucket adapters), API (each route, with the in-memory bucket and the test settings file), web (the Settings section's states), desktop (the settings kept by the app), and the journey above against the fake R2.
