# FF-223 Correlation IDs from the composition, and one entry per use case

**Status:** to do · **Group:** 16. Internal improvements

## Why

Two places go round the architecture's own rules. The HTTP adapter's error handler imports an outbound adapter to make correlation IDs, instead of being given them, so the error tests can't know the ID in advance. And `ListRolls` has two entry points, where design section 13.5 says a use case has one `execute`.

## What

`createApp` is given a function that makes correlation IDs, and the composition roots supply it: ULIDs on this machine, sequential in memory. The versioned listing of rolls becomes its own use case, `GetRollNumberingSnapshot`. Nothing a client sees changes. _(Recommendation R10 of the architecture review, items 3 and 5.)_

## Acceptance criteria

- [ ] `adapters/inbound/http/middleware/error-handler.ts` no longer imports from `adapters/outbound/`; `errorHandler` takes a `newCorrelationId: () => string` with its `reportError`.
- [ ] `createApp`'s config has `newCorrelationId`, passed to `errorHandler`. `composeLocal` supplies ULIDs (as now, through `newUlid` or the `IdGenerator`), and `composeInMemory` a sequential one.
- [ ] A 500's body carries the correlation ID, and the reported error the same ID, as now; an error test in memory now checks the exact ID.
- [ ] `ListRolls` has only `execute`. `GetRollNumberingSnapshot` (`application/use-cases/rolls/get-roll-numbering-snapshot.ts`) has the one `execute` that `executeVersioned` was, and `GET /api/rolls/numbering` uses it.
- [ ] `GET /api/rolls` and `GET /api/rolls/numbering` answer as now; every API test passes unchanged except the correlation ID check made exact.

## Not in this task

- Domain types and pure code (FF-222).
- Changing what the error response says.
