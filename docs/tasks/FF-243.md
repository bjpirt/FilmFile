# FF-243 Prepare a release

**Status:** to do · **Group:** 10. Desktop app

## Why

Starting a release in one command: the next version and its changelog worked out for me, in a pull request I can read and correct before anything is published.

## What

`pnpm release patch` (or `minor`, `major`), run on an up-to-date `main`, works out the next version from the root `package.json`, sets it there, adds an entry to `CHANGELOG.md` from the commits since the last release, and opens a pull request "chore: release 0.4.0" on a branch of its own. Merging it publishes the release (FF-244). _(Split from FF-195.)_

## Acceptance criteria

- [ ] `pnpm release patch`, `minor` or `major` works out the next version from the root `package.json`: from `0.3.2`, patch gives `0.3.3`, minor `0.4.0` and major `1.0.0`. A unit test covers the rule.
- [ ] Before any release has been made (no `v*` tag), the version is kept as it is: the first release is `0.1.0`, whichever is chosen.
- [ ] If the version in `package.json` hasn't been released yet (no tag for it) but an earlier one has, it refuses: "0.4.0 hasn't been published yet. Run the Release workflow on main to publish it."
- [ ] It sets the version in the root `package.json` only (FF-194), and adds the entry at the top of `CHANGELOG.md`.
- [ ] The entry is headed "## 0.4.0 (2026-11-20)". Under it come "### Added" (the `feat:` commits) and "### Fixed" (the `fix:` commits) since the last `v*` tag, one line each, with the commit's subject and short hash. Other commits are left out, and so is a heading with nothing under it. The first release's entry says "The first release." A unit test covers the entry.
- [ ] It commits both, as "chore: release 0.4.0", on a new branch `release/0.4.0`, pushes it and opens a pull request with that title and the entry as its description, then prints the pull request's link.
- [ ] It refuses, changing nothing, when it's not on `main`, `main` isn't up to date with GitHub's, there are uncommitted changes, the choice isn't patch, minor or major, or `release/0.4.0` already exists. Each says why.

## Not in this task

- Publishing the release when the pull request is merged (FF-244).
- Preparing a release from GitHub's Actions tab (FF-245).
- Pre-releases, and releases from another branch.

## Notes

- D125. A small script of our own, `scripts/release.ts` (Node, no dependency): the version and the changelog entry are worked out by plain functions, unit tested, from `git tag` and `git log`; the git and `gh` commands around them are kept thin. It opens the pull request as me, with `gh`, so CI runs on it (a pull request opened by a workflow's own token wouldn't start CI).
- The pull request is where the changelog's wording is corrected before it's published. Whether the script also turns on auto-merge is decided when this task is refined.
