# FF-212 A roll's reads and writes in one place

**Status:** to do · **Group:** 16. Internal improvements

## Why

Components call the API client directly, so the rules about a roll's data are written again wherever it's used. The query for one roll is defined in four places, each with its own fetch, and they must agree on what's cached with nothing checking that they do. Each write on the roll page checks the 409 and decides what to refresh by hand. The equipment and events features already keep their data in one place (`useCameras(api)`); rolls, the biggest feature, should too.

## What

Two files own a roll's data. `rolls/use-roll.ts` holds the query keys and the one definition of the roll query; `rolls/roll-changes.ts` holds one function per write the roll page makes, each owning its `If-Match`, its 409 check and what it refreshes. The roll page and the other three readers use them. No new library, and nothing a person sees changes. _(Recommendation R7 of the architecture review, for rolls; the first of the web tasks, before FF-213.)_

## Acceptance criteria

- [ ] `apps/web/src/rolls/use-roll.ts` exports the query keys as functions (`rollKey(rollId)`, `rollsKey`), the roll as read (`ReadRoll`: the roll and its ETag), and `useRoll(api, rollId)`, the one definition of the roll query.
- [ ] The query for one roll is defined only there: `rolls/roll-page.tsx`, `frames/roll-frame-page.tsx`, `rolls/use-rate-frame.ts` and `frames/use-save-frame.ts` use `useRoll`, `rollKey` and `ReadRoll` instead of their own, and the two private `ReadRoll` interfaces go. (`use-rate-frame.ts`'s `readRoll`, which reads outside a component through `queryClient.query`, uses a `rollQuery(api, rollId)` options object exported beside `useRoll`, so both share one fetch.)
- [ ] The list of rolls (`GET /api/rolls`, key `['rolls']`) is defined once too, as `useRollList(api)` (and a `rollListQuery(api)` options object for `useQueries`) in `use-roll.ts`, and used in the seven places that define it now.
- [ ] `apps/web/src/rolls/roll-changes.ts` has one function for each write the roll page makes: save a frame's number, delete selected frames, give selected frames details, delete a frame, delete the roll, save a renumbering, save the roll's details, and file or unfile the roll.
- [ ] Each takes the client, the query client, the roll as read (for its ETag) and the change, and returns `'saved' | 'changed-elsewhere' | 'failed'` (a write that gives back more, such as validation issues for the roll's details, adds that to its own result). Each sends `If-Match`, turns a 409 into `'changed-elsewhere'`, and refreshes what it refreshes now, with the comment saying why moved with it.
- [ ] `roll-page.tsx` calls them; each handler is a few lines: call, then set local state from the outcome.
- [ ] `roll-page.test.tsx`, the other web tests and the Playwright journeys pass unchanged. If a test needs changing, behaviour has changed: stop and look.
- [ ] Each new function has a test, through a fake fetch as the page tests do, for `'saved'`, `'changed-elsewhere'` (a 409) and `'failed'`.

## Not in this task

- Splitting the roll page into modes (FF-213).
- Frames, sites and events (FF-214 to FF-216). `use-save-frame.ts` only swaps its roll query and type for `useRoll`'s here; its writes stay.
- `useMutation`: plain async functions returning a small union match what the components already expect.
