# FF-239 A sync that didn't finish carries on

**Status:** to do · **Group:** 17. Sync and backup

## Why

A first sync of a big library takes hours, and gets cancelled, interrupted or cut off. Today the next sync uploads everything again: the files a cut-short sync sent are in the bucket, but only the manifest, written when a sync finishes, says what's there. FF-225 promised the next sync sends only what's still missing; this makes it true.

## What

Before uploading, a sync lists the bucket and skips any file already there at its path whose ETag matches the file's MD5, so a sync carries on wherever the last one stopped. This applies to every sync, first or later. Nothing is kept on this computer to do it, and the bucket's sync record and manifest are written as before, only when a sync finishes (D117, D122).

## Acceptance criteria

- [ ] A first sync cancelled after some files were sent, then started again, uploads only the files not yet in the bucket. Its progress counts only those.
- [ ] The same after a sync that failed part-way, after the service was stopped mid-sync, and with the cache folder cleared.
- [ ] A later sync that didn't finish carries on in the same way.
- [ ] A file changed after it was sent in a sync that didn't finish is sent again, because its MD5 no longer matches.
- [ ] A file in the bucket whose ETag isn't an MD5 (such as S3 with KMS encryption, later) is sent again, never wrongly skipped.
- [ ] A sync that finishes writes the manifest with every file the bucket holds for the library, whether sent in this sync or found there, each with its SHA-256.
- [ ] The bucket is listed only when there's something to upload. With nothing changed, a sync makes no listing.
- [ ] The bucket's sync record and manifest stay as they were after a sync that didn't finish (FF-225).

## Not in this task

- Saying anything new in Settings: the wording about carrying on comes with FF-240 and FF-241.
- Cancel cutting off the uploads under way (FF-240), and the whole library's progress (FF-241).

## Notes

- **Decisions:** D117 (the record and manifest are written last), D120 (the hash cache), D122 (the bucket checked by MD5 before uploading).
- **Hashes:** the hash cache (`FilesystemLibraryFiles`) also keeps each file's MD5, worked out in the same read as its SHA-256. `ManifestEntry` stays path, size and SHA-256; the library's description gains `md5`. A cache entry without an MD5, from FF-225, is hashed again once.
- **Planning:** `planBackup` takes the bucket's listing (`PublishBucket.list`, which already gives each key's size and MD5) as well as the manifest. A planned upload whose key is listed with the same size and MD5 is moved to "already there", and the manifest records it with the library's SHA-256.
- **Tests:** start with a failing API test that really sends some files before cancelling. FF-225's test "a sync that fails part-way … the next sends only what is missing" passed only because the in-memory bucket failed every upload already under way, so no file had been sent. Fix it to send some first. Also unit (planning with a listing: a match, a different MD5, a different size, a non-MD5 ETag) and the hash cache's contract (MD5 kept, and an old entry re-hashed).
