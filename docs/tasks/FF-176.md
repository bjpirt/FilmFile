# FF-176 Export several frames straight into a folder in the desktop app

**Status:** done · **Built in:** 12. Exports

## Why

In the desktop app, an export of several frames should land as JPEGs in the folder I want (a Lightroom folder, Dropbox, a print shop's USB stick), ready to use, not as a zip I then have to open.

## What

In the desktop app, "Download" in the Export dialog for several frames (FF-167, FF-168) asks for a folder with the computer's own folder chooser, and the service writes the JPEGs straight into it, with the layout and file names chosen, while the dialog shows its progress. A browser keeps the zip, and a single frame in the frame view keeps FF-166's save dialog.

## Acceptance criteria

- [x] In the desktop app, "Download" for several frames opens the system's folder chooser, starting in the folder last used (the Downloads folder the first time); cancelling it makes and writes nothing, and the dialog stays open.
- [x] Choosing a folder writes a JPEG of each frame into it, made as in FF-165 and laid out and named as chosen (including `A folder per roll` and `Year then roll`, whose folders are made inside the chosen one); the dialog says "Exporting 4 of 12…" as it goes, with a "Cancel" that stops the work, leaving the files already written.
- [x] A file that would have the same path as one already there is written with `-2`, `-3` after its name; nothing already in the folder is ever replaced or changed.
- [x] A file is written whole or not at all: a stopped or failed export leaves no half-written JPEG.
- [x] A frame that can't be made is left out and listed in a `skipped.txt` in the chosen folder with why, as in the zip (FF-167).
- [x] When it's done the app says "Saved 12 files to /Users/ben/Pictures/Iceland" with a "Show in Finder" button, and the folder is remembered, per computer (D52).
- [x] In a browser, and for a single frame in the frame view, nothing changes: the zip and the JPEG download as before.
- [x] The page never sends a folder: no request can make the service write anywhere that wasn't chosen in the app's own dialog, and only to the folder chosen.
- [x] A failure (the folder is full or can't be written to) says what went wrong without internals, and keeps the files already written.

## Not in this task

- Saved exports (FF-116, FF-117), always made in `Exports/<slug>/` in the FilmFile folder.
- Exporting a single frame to a folder: it keeps FF-166's save dialog, where its name is chosen.
- Overwriting or asking about files already there.

## Notes

- D100. The page asks as it does for a zip, with `output: 'folder'`; it learns the service can do this from a capability in the settings or health response, set when the service has a parent app to ask (so there's no environment variable to set). The service asks its parent over the utility process's message channel for a destination; the app shows `dialog.showOpenDialog` and replies with the folder or a cancel. The page can't reach that channel.
- A new port, `ExportDestination` (adapters: the parent process over its message channel, and an in-memory one for tests, with a contract suite), gives the service a folder it may write to; every path is made through the safe-path helper, confined to that folder, and written by a temporary name then renamed.
- The naming, layout and `-2` rules are FF-167's `export-names.ts` (a `FilePaths` that also checks what's already in the folder), and the rendering is `MakeQuickExport`'s, shared with the zip.
- Progress: `POST /api/exports/folder` answers once the folder is chosen, with an export to follow (or none if the person cancelled); the page polls `GET /api/exports/folder/{job}` and cancels with `DELETE` on it.
- The `security-rules` skill and `docs/design.md` change with it: the service writes nothing outside the FilmFile folder *except* to a folder the person chose in the desktop app's own dialog, for that export only.
- Tests: the use case and API against the in-memory destination (layout, `-2`, `skipped.txt`, cancel, no half files), the contract suite, the app's message handling as a unit test over fakes, the dialog's progress, and a desktop journey that answers the folder chooser (as FF-166's does for the save dialog).

## What was built

The service has a new `ExportDestination` port (`choose()` a folder, `finished()` to tell the app) and an `ExportFolder` to write into, with adapters for the parent process (`adapters/outbound/node/parent-process-export-destination.ts`, over Electron's `process.parentPort`), the filesystem (`filesystem-export-folder.ts`: single names under the chosen folder, a temporary name then a rename, `-2` for a taken name) and memory, and a contract suite for the folders. `FolderExports` (`application/use-cases/exports/folder-exports.ts`) checks the frames, asks for the folder and writes in the background, reusing `MakeQuickExport.entries` (the zip's entries, `skipped.txt` included); `POST /api/exports/folder`, `GET` and `DELETE /api/exports/folder/{job}` are its routes, and `GET /api/health` says `exportToFolder`. The desktop app (`service-messages.ts`, `main.ts`) answers the service's request with its folder chooser, remembers `exportFolder`, and says "Saved 10 files to …" (and what was left out) with "Show in Finder". The Export dialog asks the health response, writes into a folder for several frames when it can, and shows "Exporting 4 of 12…" with Cancel. Tests: the folder contract suite, the use case through the API (layout, `-2`, `skipped.txt`, the chooser cancelled, cancel mid-way, no desktop app), the parent-process adapter and the app's messages over fakes, the dialog, and a desktop journey.
