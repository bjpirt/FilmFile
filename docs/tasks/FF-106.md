# FF-106 Change a roll's number

**Status:** to do · **Group:** 2. Roll numbers · **Was:** U25

## Why

A roll's number is only a guess until its negatives are filed: a wrong year, or a roll that should come before another, is put right by hand, and no two rolls may ever share a number.

## What

Edit details has a Roll number field, the first, like New roll's; changing it renames the roll's folder to match (`2026-009-Q2P7RM4K`, FF-151). No two rolls can have the same number: the roll repository refuses a number another roll has (D70). Refusing a filed roll's number change is FF-107's. *(From 1.3.15, 1.4.3 and 1c.2.)*

## Acceptance criteria

The page:

- [ ] Edit details has a "Roll number" field as its first, with the required star, the placeholder `2026-014` and the numbers font, as on New roll, filled with the roll's number.
- [ ] A number that isn't `YYYY-NNN` is refused before anything is sent: "Enter a roll number like 2026-014: the year it was shot, then three digits."
- [ ] A number another roll has is refused: "Roll 2026-009 already exists.", and nothing is saved.
- [ ] Saving a changed number shows it at once, without reloading, in the roll's heading and breadcrumb, on the rolls page (in its new place in the order), on its frames' pages ("Roll 2026-009 / Frame 12") and on event pages.
- [ ] The roll's address and links to it and its frames don't change, as they use its ID.
- [ ] The number is sent only when it was changed: an untouched or restored number isn't sent, so saving the name or notes never depends on it.
- [ ] A number whose year isn't the year shot is saved as it is, with no warning; so is changing the date shot without the number.
- [ ] Renumbering a roll that has raw scans asks nothing and warns of nothing.
- [ ] A change refused because the roll changed (409) says so ("The roll changed since you opened it. Reload the page.") and changes nothing.

The API:

- [ ] `PATCH /api/rolls/{rollId}` takes `roll`, a well-formed number (`YYYY-NNN`): it changes the roll's number, keeps its ID, and answers with the roll and its new ETag; a malformed number is a 422 with an issue on `roll`.
- [ ] A number another roll has is a 422 with an issue on `roll` ("is already used by another roll"), not a 409, which stays for "changed since it was read".
- [ ] The roll repository refuses, atomically, a save or change that would give a roll another roll's number, and so does creating one; two requests can never both take a number.
- [ ] The roll's folder on disk is renamed to `<new number>-<ID>` (FF-151), moving to the new number's year; the rolls list is in the new order.
- [ ] A rolls page opened before the change still opens the roll by its ID.

## Not in this task

- Refusing to change a filed roll's number, and showing it as not changeable (FF-107).
- Numbering many rolls at once, and swapping numbers through the API (FF-108).
- Warning when the number's year differs from the year shot.

## Notes

- Needs FF-151 (the folder naming and renaming).
- Decision D70. The `RollRepository` port's `save` and `change` can now fail with `AlreadyExists`, checked under a lock with the number change, so rolls can no longer swap numbers one save at a time: FF-151's swap test uses a spare number, and FF-108's batch operation validates the final state instead.
- The page checks the format itself before sending, so a 422 on `roll` from the service means the number is taken.
- The use case, `UpdateRoll`, takes `roll` as it takes the other details; its number's year doesn't have to match the date shot (D7's "year shot" is a convention for new rolls).
- Tests: page tests for the field, the two refusals, showing the new number, and sending only a changed number; API tests for the route, the 422s and the folder on disk; the repository contract suite for uniqueness (create, save and change); the "Catalogue a roll" journey gains a step: change the roll's number in Edit details, see it in the heading and on the rolls page, and reload. The final check runs everything.
