# FF-206 One lock in the roll repository

**Status:** to do · **Group:** 16. Internal improvements

## Why

The roll repository is the hardest file in the backend to read, and part of that is three nested locks where one does the work. D77 already describes the design as one in-process lock; the code should say the same.

## What

The filesystem roll repository keeps only its archive-wide lock, and the in-memory one only its `#writes` lock. The inner locks, which can never be contended because they're only ever taken inside the archive-wide one, go, and the callbacks they wrapped are un-nested. Nothing changes in behaviour. _(Recommendation R5a of the architecture review; the first of three tasks slimming the repository, before FF-207 and FF-208.)_

## Acceptance criteria

- [ ] `FilesystemRollRepository` has one lock, `#archive`; `#lock` (per roll) and `#years` are gone.
- [ ] `InMemoryRollRepository` has one lock, `#writes`; `#lock` is gone.
- [ ] Every operation that took an inner lock still runs inside the remaining one.
- [ ] The concurrency tests (`apps/backend/test/api/concurrency.test.ts`), the roll repository contract suite's concurrent cases and the filesystem adapter tests pass unchanged.

## Not in this task

- Moving the renumbering rules (FF-207) or the folder moves (FF-208).
- Changing what's locked or for how long.
