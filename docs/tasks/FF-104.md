# FF-104 Mark frames to scan

**Status:** done · **Built in:** 6. Versions and scans · **Was:** U22a

## Why

While looking through a roll, I can keep a durable selection of frames I intend to scan at higher resolution and distinguish work still pending from frames already scanned.

## What

Add a persistent `toScan` mark to each frame. Set or clear it from the frame view or in bulk. Show the pending mark on thumbnails, and show a related “Scanned” mark when a Raw scan or Final exists. A Raw scan or Final does not erase the selection; the roll count and future scan list count only marked frames that still need a Raw scan or Final. *(Split from U22.)*

## Acceptance criteria

- [x] A frame with no `toScan` field in `roll.json` reads as `false`; a saved frame stores `toScan: true` only when marked. The frame API always returns a boolean `toScan` and accepts an optional boolean in single and bulk updates.
- [x] The frame view has a scanner icon button beside the other frame actions. Its tooltip and accessible name are “Mark to scan” when clear and “Marked to scan” when set; activating it toggles the mark. The button uses the yellow theme accent whenever marked, regardless of scan completion, and is neutral when clear. A numbered or unnumbered frame can be marked.
- [x] In bulk edit, Set ▸ “Mark to scan” marks every selected frame, and Set ▸ “Unmark” clears every selected frame, in one versioned roll save. Success reads “2 frames marked to scan.” or “Scan mark removed from 2 frames.”, with singular grammar for one frame.
- [x] A pending marked frame shows a neutral scanner icon in the thumbnail mark row (U69, U70), named “To scan at higher resolution” for screen readers and on hover.
- [x] A marked frame that has at least one Raw scan or Final shows the thumbnail scanner-with-check icon in orange, named “Scanned”. The mark remains set; adding a Raw scan or Final does not clear it.
- [x] The roll heading appends the pending count to its frame count, e.g. “6 frames (2 to scan)”. It counts marked frames without a Raw scan or Final, uses “1 to scan” for one, and has no to-scan suffix when none are pending.
- [x] Deleting the last Raw scan and Final from a marked frame keeps the mark and returns it to the pending “To scan at higher resolution” state.
- [x] Renumbering a frame does not change its mark; its status remains attached to the frame ID.
- [x] A save refused because the roll changed (409) leaves the mark unchanged and uses the existing message: “This roll changed since you opened it. Reload the page.”
- [x] The later FF-131 scan list includes marked frames only while they have no Raw scan or Final; already-scanned marked frames are omitted.
- [x] The “Bulk edit” journey covers setting and clearing marks and seeing the thumbnail states; the existing Raw scan upload behavior continues to pass.

## Notes

- Decisions D85–D86. D85 sets the persistent mark lifecycle and `toScan` storage/API shape; D86 sets icon state/color and accessible text, toolbar control, count format and bulk feedback.
- A frame is “Scanned” when any version is kind Raw scan or Final. Removing all such versions does not clear `toScan`; it becomes pending again.
- `toScan` is frame state, not inherited metadata. Missing persisted values default to false; no schema bump or migration is needed.
- The scan list in FF-131 consumes the pending subset only. FF-116 has a separate export mark and is not part of this task.

## What was built

Frames now persist `toScan` only when true, defaulting to false for existing records, and expose its boolean value through frame reads and single/bulk updates. The frame view has an icon-only scanner toggle beside its other actions; its tooltip and accessible name say Mark to scan or Marked to scan. Bulk edit has Mark to scan and Unmark actions. Thumbnails show a neutral scanner while pending and an orange scanner with a check when a marked frame has a Raw scan or Final. The roll heading counts only marked frames still lacking either kind. Adding or deleting Raw/Final versions does not clear the selection; a marked frame returns to pending if its last Raw/Final is deleted.

The OpenAPI client, filesystem persistence tests, API tests, use-case tests, web tests and Bulk edit journey cover this behavior. The scan-list and raw matching workflow remains FF-131.
