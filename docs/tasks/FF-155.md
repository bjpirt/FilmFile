# FF-155 Frame and version folders named by number and kind

**Status:** to do · **Group:** 2. Finding your way around the library

## Why

In Finder, a roll's frames and versions should be recognizable without opening `roll.json`. Naming their folders by frame number and version kind makes the library readable while IDs keep each name unique.

## What

Store each version at `frames/<frame number>-<frame ID>/<kind>-<version ID>/<original name>`, using the last 8 characters of each ULID. Rename the frame folder when its number changes and the version folder when its kind changes; keep the version's relative path in `roll.json` in step with each move (D69). This task supports only the new layout; it does not migrate or support ID-only frame/version folders.

## Acceptance criteria

- [ ] A frame with a version has a folder named `frames/<cleaned frame number>-<frame ID>/`, or `frames/unnumbered-<frame ID>/` when its number is null. The ID is the last 8 characters of its ULID.
- [ ] A frame-number label keeps ASCII letters, digits and hyphens; each other character becomes `_`. A leading hyphen is prefixed with `_`. For example, `14-15` stays `14-15`, `12/13` becomes `12_13`, `.12` becomes `_12`, and `-12` becomes `_-12`.
- [ ] An empty frame has no physical folder; its folder is created when its first version is stored.
- [ ] A version folder is named `scan-<ID>`, `raw-scan-<ID>` or `final-<ID>`, using the last 8 characters of its ULID. Its files and sidecars keep their original names.
- [ ] Changing a frame's number renames its frame folder; changing a version's kind renames its version folder. The corresponding `roll.json` paths are saved with the metadata change, and no file contents or names change.
- [ ] Renumbering multiple frames in one roll, including swapping their numbers, renames all affected folders without collisions.
- [ ] A missing source folder for a frame/version that has files, or an occupied destination folder, fails the save without overwriting anything or changing `roll.json`. A frame with no versions needs no source folder.
- [ ] If an ordinary filesystem or metadata-save failure happens after a move, the service makes a best-effort rollback. It reports failure if rollback is incomplete; crash recovery is covered by FF-156.
- [ ] Creating, reading originals and thumbnails, and deleting frames or versions work with the new paths. API responses still contain no filesystem paths, and browser journeys have no visible change.

## Not in this task

- Migrating or supporting archives with ID-only frame/version folders; this pre-release layout has no backwards-compatibility guarantee.
- Recovering a rename interrupted by a process stop or incomplete rollback (FF-156).
- Refreshing NegPy links automatically during a rename; they are rebuilt the next time the user chooses "Open in NegPy" (FF-112).
- Renaming original files, which keep their original names.

## Notes

- D69 replaces D17 and D58. D79–D82 record the label rule, new-layout-only scope, filesystem failure behavior and NegPy refresh timing. `roll.json` remains the source of each version's relative file path; API DTOs do not expose it.
- Frame folders are lazy because a frame can exist without versions. New version uploads create the frame and version folders together.
- A rename changes paths, so backup and sync see the files as new; moving raw scans can trigger another Glacier minimum-storage charge. Frames are mostly renumbered before their raws are added.
- Tests: filesystem, repository contract and API tests cover new paths, cleaning, frame/kind changes, swaps, missing folders and collisions. Existing browser journeys remain unchanged.
