# FF-242 Protect main

**Status:** to do · **Group:** 10. Desktop app

## Why

Nothing reaches `main` without CI passing, and its history can't be rewritten or lost by mistake, now that merging to it will publish releases (FF-244).

## What

A GitHub ruleset on `main`: changes come in by pull request once CI passes, with no review needed (I work alone), and `main` can't be force-pushed or deleted. Auto-merge is turned on, so a PR merges itself when it's green. Work moves from committing on `main` to a branch and a pull request for each task, in CLAUDE.md and the README.

## Acceptance criteria

- [ ] Pushing a commit straight to `main` is refused.
- [ ] A pull request to `main` can't be merged until CI's jobs have passed on it; no approving review is needed.
- [ ] `main` can't be force-pushed or deleted.
- [ ] A pull request can be set to merge itself once CI passes ("Enable auto-merge").
- [ ] The ruleset's settings are written down in `docs/` (where to find it on GitHub, and each rule), so it can be set up again.
- [ ] CLAUDE.md and the README say how work reaches `main`: a branch for each task, committed when asked, pushed and opened as a pull request when asked.

## Not in this task

- Preparing and publishing releases (FF-243, FF-244).
- Protecting `v*` tags: only people who can write to the repository can push them, and that's only me.

## Notes

- D126. The ruleset is set by hand in the repository's settings (Settings › Rules › Rulesets); nothing in the repository applies it.
- The required checks are CI's job names (`verify` on each OS, the packaged app, the journeys); when a job is renamed or added, the ruleset changes with it.
- Whether I can bypass the rules, for an emergency, is decided when this task is refined.
