# FF-238 Renames and removals in the backup

**Status:** to do · **Group:** 17. Sync and backup

## Why

After the first backup (FF-225), the bucket should follow the library as it changes. A renumbered roll or frame shouldn't be uploaded all over again, and a file emptied from `deleted/` shouldn't stay in the backup for ever. A file gone missing from this computer, though, must never take the backup's copy with it.

## What

Sync copies a renamed file inside the bucket instead of uploading it again, and removes the old copy. Other files that have gone from the library and that no `roll.json` mentions are removed too, but only once the person agrees. The sync pauses after checking to ask, before it changes anything. A file a `roll.json` still mentions that's missing on this computer is kept, and the sync says which. _(Split from FF-225.)_

## Acceptance criteria

- [ ] A file whose folder was renamed (a renumbered frame or roll, a version's changed kind) is matched by its SHA-256 to a file the bucket's manifest has. It's copied inside the bucket from there, not uploaded again, and its old path is removed without asking.
- [ ] Copies are counted in the upload progress's files but not its bytes: "Uploading 1.2 GB of 3 GB (12 of 34 files)", where the 34 includes the copies. The time left is worked out from bytes uploaded only.
- [ ] A copy whose source the bucket doesn't have (removed by hand, say) is uploaded instead, and the sync finishes as normal.
- [ ] A renamed file the bucket already has at its new path, with a matching MD5, is neither copied nor uploaded (as FF-239 does for uploads).
- [ ] A file in the bucket's manifest is removed from the bucket only when it has gone from the library and no `roll.json` in the library mentions it (D117). That covers files emptied from `deleted/`, a site's old file after renaming it, and a roll folder deleted in Finder.
- [ ] When there are such files, the sync pauses after checking the library and the bucket, before sending anything. Settings and the panel read "This sync will also remove 3 files from the backup that are no longer in the library (1.2 GB).", with "Show files" listing their paths in the library (up to 50, then "and 12 more"), and the buttons "Remove them" and "Keep them for now". "Cancel" still stops the sync.
- [ ] While it waits, the header reads "Waiting…", and the question stays until it's answered or the sync is cancelled, including across a reload.
- [ ] "Remove them" carries on and removes them. "Keep them for now" carries on without removing them: they stay in the bucket and its manifest, and the next sync asks again.
- [ ] A file a `roll.json` mentions but that's missing on this computer is never removed from the bucket, and stays in the manifest. The finished sync says "2 files that were backed up are missing on this computer. The backup still has them.", with "Show files" listing their paths (up to 50, then "and 12 more").
- [ ] The finished sync names only what happened, in one line: "Sent 12 files (1.2 GB), copied 36 renamed files and removed 3 files from the backup." A sync that only sent files reads as now.
- [ ] Removals come after uploads and copies, and before the manifest and sync record. A sync cut short during them leaves the record and manifest as they were, and the next sync plans the removals again.
- [ ] `GET /api/sync` gives the state `waiting` with the files to remove (count, bytes, up to 50 paths and how many more), and the finished sync's copied, removed and missing counts with the missing paths. `POST /api/sync/removals` with `{ "remove": true }` or `{ "remove": false }` answers it, and is 409 when nothing is waiting. All are in the OpenAPI spec.

## Notes

- **Decisions:** D117 (a file leaves the bucket only when no `roll.json` mentions it and it's gone from the library; one that's mentioned but missing is damage), D123 (asking about every removal but renames, keeping for now, and how copies count).
- **Mentioned by a `roll.json`:** each version in `roll.json` records its folder and its file's name, with the file's SHA-256, so the sync can tell exactly which missing files are catalogued.
- **Planning:** `planBackup` gains copies (a library file at a path the manifest hasn't got, whose SHA-256 the manifest has at a path the library no longer has), removals (the manifest's paths gone from the library, other than renames' old paths, and mentioned by no `roll.json`) and missing files (gone and mentioned). `manifestAfter` drops what was removed, and keeps what's kept and missing.
- **Requests:** the bucket port gains `copy` (S3's `CopyObject`, with `x-amz-copy-source`), and removals use FF-201's delete-many.
- **State:** `SyncProgress.state` gains `waiting`, held by the job until `POST /api/sync/removals` or a cancel.
- **Tests:** unit (planning copies, removals and missing files from the library, its `roll.json` files and the last manifest), contract (copy, and copy from a key the bucket hasn't got), API (copies with no upload, the fallback upload, the pause and both answers, cancelling while waiting, missing files kept, a sync cut short during removals), and web (the question, "Waiting…", the finished message and both "Show files" lists). The backup journey is extended: renumber a frame and sync ("copied … renamed files", nothing sent); then delete a frame, empty `deleted/` on disk, sync, and answer "Remove them".
