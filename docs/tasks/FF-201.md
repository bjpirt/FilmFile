# FF-201 Publish a site to Cloudflare

**Status:** later · **Group:** 13. Sites

## Why

Putting a built site on the web, on Cloudflare, without other tools, and keeping it in step with the archive in one click.

## What

A "Publish" section on the site's page, below Build, says where the site goes in a Cloudflare R2 bucket (account ID, bucket, an optional folder, and the address it's seen at), and whether what's there matches the site. "Publish" builds the site as needed, then uploads only what differs and removes what's gone, with progress and "Cancel". "Unpublish" removes it, after asking. The keys come from the `[filmfile]` profile in `~/.aws/credentials`, so FilmFile keeps no keys (D111). _(Split from FF-121.)_

## Acceptance criteria

- [ ] The site's page has a "Publish" section below Build, with fields "Cloudflare account ID", "Bucket", "Folder" (optional) and "Address", saved with the site as they're changed, like its other details. Until account ID, bucket and address are filled in, it reads "Say where to publish the site." and "Publish" is disabled.
- [ ] A field that isn't valid says why under it and isn't saved: an account ID that isn't 32 hex characters, a bucket name R2 wouldn't take, a folder that isn't a plain relative path (no `..`, no leading `/`), an address that isn't an `https://` URL.
- [ ] When the page opens, with a target set, the section says how the bucket stands, from a listing of the site's folder: "Not published", "Published 13 Nov 2026, 14:02, up to date" or "Published 13 Nov 2026, 14:02: 12 files to update" (the date from `index.html` in the bucket), comparing against the built site by path, size and MD5. While it's asking it reads "Checking what's published…".
- [ ] "Publish" builds the site first when it isn't built or is out of date, as "Build site" would ("Making images: 12 of 40"), then uploads ("Uploading 12 of 40"), with "Cancel" throughout. When it's done it reads "Published 13 Nov 2026, 14:02, up to date", with "View site" opening the address.
- [ ] Only files that are missing or differ are uploaded, and files under the site's folder that the built site no longer has are removed. Publishing again with nothing changed uploads and removes nothing.
- [ ] Images go up first, then pages, CSS and script, then removals, so a cancel or failure part-way leaves the published pages working as they were. A cancelled publish reads "Publishing cancelled."
- [ ] Each file is sent with its content type. Images get `Cache-Control: public, max-age=31536000, immutable`; pages, CSS and script `public, max-age=300`. `site.json` is never uploaded.
- [ ] "Unpublish" asks "Unpublish Iceland? This removes 2,104 files from photos-pirt." (from "photos-pirt/iceland/" when there's a folder), with "Unpublish" and "Cancel". It removes everything under the folder, the whole bucket when there's none, and nothing outside it. It then reads "Not published". With nothing published it's disabled.
- [ ] Build, Publish and Unpublish are disabled while any of them runs for the site, and while a change to the site is being saved.
- [ ] Each failure says what to fix, and anything already uploaded stays:
  - "No [filmfile] profile in ~/.aws/credentials, so the site can't be published."
  - "Cloudflare refused the keys in the [filmfile] profile."
  - "There's no bucket photos-pirt in that Cloudflare account."
  - "Couldn't reach Cloudflare. Are you online?"
  - "Couldn't publish the site." for anything else, with no internals.
- [ ] The API: `GET /api/sites/{slug}/published` (how the bucket stands), `POST /api/sites/{slug}/publish` (start, 202, followed with the same status as builds), `DELETE /api/sites/{slug}/publish` (cancel) and `DELETE /api/sites/{slug}/published` (unpublish). All are in the OpenAPI spec.

## Not in this task

- S3 (FF-200), which reuses this task's bucket port and signing with AWS's endpoint.
- Choosing a profile name, or a Settings section for publishing: the profile is always `[filmfile]` until someone needs two.
- Setting up the bucket, its custom domain, and the rewrite rule that serves `/index.html` at `/`. The task's notes say how, by hand.
- Cloudflare Pages or Workers static assets (capped at 20,000 files free, 100,000 paid), and publishing automatically on a change (workflows, design §11).

## Notes

- **Why R2 (D111):** no limit on files (a site is about 5 files a photo), free downloads, $0.015/GB-month past 10 GB, and S3's API, which FF-200 shares. Every link in a built site names its `.html` file, so only `/` needs the rewrite rule.
- **Data:** the target is kept with the site in `Library/sites/<slug>.json`, synced, since a site goes to the same place from any computer: `publish: { accountId, bucket, folder, address } | null` (folder `""` for the bucket's root). Only the keys are per computer (D52), and they stay in `~/.aws/credentials` (or `AWS_SHARED_CREDENTIALS_FILE`), read when publishing and never stored or sent to the browser. This updates D92, whose targets were per computer.
- **Requests:** our own `fetch` to `https://<accountId>.r2.cloudflarestorage.com`, signed with AWS Signature Version 4 (region `auto`, service `s3`) using `node:crypto`; no SDK (a few lines of our own will do). ListObjectsV2 (1,000 per page), PutObject, DeleteObjects (1,000 per request). R2's ETag for a single-part upload is the file's MD5. The credentials file is parsed by a few lines of our own.
- **Ports:** a `PublishBucket` port (list, put, delete many), with an in-memory adapter and the R2 adapter, both run through one contract suite. The R2 adapter runs against a small local HTTP server speaking enough of S3's API, which also checks the signature. The use case reuses `SiteBuilds` to build first, and keeps one job per site like it.
- **Security** (the `security-rules` skill): outbound requests go only to the account's R2 host; the account ID, bucket and folder are checked by Zod at the boundary; errors carry no internals; the address is only ever a link.
- **Tests:** unit (signing against AWS's published examples, the credentials file, the plan of uploads and removals), contract (both bucket adapters), API (each route, with the in-memory bucket), web (the section's states and messages from the fake archive), and a journey that sets a target, publishes to the in-memory bucket, sees "up to date", changes a frame, sees "files to update", and unpublishes.
- **Checking by hand against real R2:** make a bucket and an R2 API token with read and write on it, put its access key ID and secret in `~/.aws/credentials` under `[filmfile]`, connect a custom domain to the bucket, and add a URL rewrite rule from `/` to `/index.html`.
