# FF-244 Publish a release

**Status:** to do · **Group:** 10. Desktop app

## Why

Merging a release's pull request publishes it: the app for every platform, built and checked the same way each time, rather than by hand on my Mac.

## What

A "Release" workflow runs when a push to `main` changes the root `package.json`. If that version hasn't been released (there's no `v` tag for it), it builds and checks the app on every platform through `package.yml`, and only if they all pass tags the commit and publishes a GitHub release with the apps, their checksums and the changelog entry. It can also be run by hand, to try again after a failure. A pull request that changes the version is built on every platform before it's merged. At first that's the two Mac disk images; Windows and Linux join when they're built (FF-197, FF-198). _(Split from FF-195.)_

## Acceptance criteria

- [ ] A push to `main` that changes the root `package.json` starts "Release". If the tag `v<version>` already exists (a change to its scripts or dependencies, say), it stops there, having done nothing.
- [ ] Otherwise it builds and runs the packaged-app journey on every platform in `package.yml`, with that version. If any of them fails, nothing is tagged or released.
- [ ] Once they all pass, it tags the commit it built `v0.4.0` and publishes the GitHub release "FilmFile 0.4.0" at once (not a draft). Its notes are the version's entry in `CHANGELOG.md`.
- [ ] The release holds every platform's file and `SHA256SUMS`, one line per file in `sha256sum`'s format, checkable with `shasum -a 256 -c SHA256SUMS`.
- [ ] Actions › "Release" › "Run workflow", on `main`, does the same for the version in `package.json`, so a release that failed is tried again once it's fixed.
- [ ] A pull request that changes the version in `package.json` also builds and checks every platform in `package.yml` in CI, so a broken build is found before merging.
- [ ] Only one release runs at a time (a concurrency group).
- [ ] Only the last job, which tags and releases, can write (`contents: write`). The build jobs read only, and no other secret is used. Actions are pinned to commit SHAs.

## Not in this task

- Bumping the version and writing the changelog (FF-243).
- Signing (FF-137, FF-199) and updates (FF-138). Until then, macOS asks before opening a downloaded app (System Settings › Privacy & Security › Open Anyway), and so will Windows SmartScreen.
- Running `pnpm verify` and the browser journeys again: the pull request's CI already has (the release checks only the packaged apps).
