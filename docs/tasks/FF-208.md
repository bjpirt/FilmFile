# FF-208 The roll repository's folder moves in their own files

**Status:** done · **Built in:** 16. Internal improvements

## Why

After FF-206 and FF-207, what still makes the filesystem roll repository long is two blocks of rename-and-roll-back code that aren't about the repository's interface. A reader should see the port's methods, each short enough to read without scrolling.

## What

Moving version folders when a frame's number or a version's kind changes, and moving roll folders in a batch through temporary names with rollback, each go into their own file as plain functions. The small filesystem helpers at the bottom of the repository go into one file they share. Nothing changes in behaviour. _(Recommendation R5c of the architecture review; the last of three tasks, after FF-207.)_

## Acceptance criteria

- [x] `apps/backend/src/adapters/outbound/filesystem/move-version-folders.ts` exports `moveVersionFolders({ current, roll, renameFolder })`: what `withChangedVersionPaths`, `versionFolderMoves` and the body of `#saveChanged` do now (the checks, the moves, removing the emptied folders, writing roll.json, and the rollback if any of it fails). It returns `{ content, version }` as `#saveChanged` does. The rest are private to the file.
- [x] `apps/backend/src/adapters/outbound/filesystem/renumber-roll-folders.ts` exports `renumberRollFolders({ stored, changes, renameFolder, removeYear })` (it works out which rolls move from the plan's changes): the batch's folder moves through temporary names and their rollback (the second half of `saveRenumberedBatch` now), including its "a destination roll folder is already in use" refusal.
- [x] `StoredRoll` (roll, version, file, content) is exported from `apps/backend/src/adapters/outbound/filesystem/stored-roll.ts`, used by the repository and `renumber-roll-folders.ts`.
- [x] `exists`, `isDirectory` and `removeIfEmpty` are in `apps/backend/src/adapters/outbound/filesystem/folder-checks.ts`, used by the repository and the two new files. The three exports are a deliberate exception to one main export per file, with a comment saying so.
- [x] The repository file holds the port's methods and what only they use, including the single-roll `#move`; each method is short enough to read without scrolling.
- [x] The repository passes `renameFolder` and `removeYear` through to the new functions, as it is given them, so tests can still make a rename fail. The version moves still use `removeIfEmpty` directly for emptied folders, as now.
- [x] A rollback that can't be completed still fails loudly, with the same `AggregateError` and messages as now (D78).
- [x] The filesystem adapter tests, the contract suite and the API tests pass unchanged, still driving the moves through the repository.

## What was built

- `adapters/outbound/filesystem/move-version-folders.ts` (`moveVersionFolders`), `renumber-roll-folders.ts` (`renumberRollFolders`), `stored-roll.ts` (`StoredRoll`) and `folder-checks.ts` (`exists`, `isDirectory`, `removeIfEmpty`).
- `filesystem-roll-repository.ts` went from 700 to 385 lines and passes `renameFolder` and `removeYear` through. The single-roll `#move` stayed in it.
- `renumberRollFolders` takes the stored rolls and the plan's changes and works out which move, not a ready-made `moving` list.

## Not in this task

- New tests for the moved functions on their own: the repository's tests already cover them at the right level.
- Changing how the moves or rollbacks work.
- Moving the single-roll `#move` out of the repository, or other parts of it (`#readAll`, the roll-folder parsing): it stays as it is.
- A line-count target for the repository file; the criterion is what it holds, not how long it is.
- Splitting the pure planning from the apply-and-rollback step, or turning the moves into classes.
