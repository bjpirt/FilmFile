# FF-218 Branded IDs without dead branches

**Status:** to do · **Group:** 16. Internal improvements

## Why

Route handlers check IDs the request schema has already checked: `if (!isRollId(rollId)) return 404`, 14 times in the rolls routes alone. The branch can never run, because the schema and the domain use the same pattern, and a reader has to work that out each time. One handler instead silently drops a frame ID that fails the check, where every other refuses.

## What

A function per kind of ID gives a checked value its branded type, or throws, since a failure would be a bug in the schema, not the client's mistake. Handlers start with one line instead of four. A test proves the schema's patterns and the domain's agree, which is what makes the guards dead. The dropped frame IDs are branded the same way, so none can be lost. _(Recommendation R8 of the architecture review, steps 2 and 4, and the matching patterns test from its "left alone" list; after FF-217.)_

## Acceptance criteria

- [ ] `asRollId`, `asFrameId`, `asVersionId` and `asSlug`, in one file under `apps/backend/src/adapters/inbound/http/`, each give the value its branded type, or throw an `Error` saying the route's schema let through a value it shouldn't.
- [ ] One unit test shows each throws on a malformed value and gives a well-formed one back.
- [ ] A test shows the contracts' patterns and the domain's agree: every value in a table of good and bad ULIDs passes `ulid` in `packages/contracts/src/rolls.ts` exactly when it passes `isRollId`, and every value in a table of good and bad slugs (including one of 60 characters and one of 61) passes `slug` in `packages/contracts/src/slug.ts` exactly when it passes `isSlug`.
- [ ] Every guard on a schema-checked ID in the route files is replaced: in the rolls routes (after FF-217, the three files), `events.ts`, `sites.ts`, `exports.ts` and `selection-body.ts`.
- [ ] Updating frame numbers (`PATCH /api/rolls/{rollId}/frames` with `numbers`) brands each frame ID with `asFrameId` instead of dropping those that fail.
- [ ] `built-sites.ts`'s guard stays: its slug comes from a plain Hono path, not a schema, so a bad one really can arrive and is answered 404.
- [ ] Every API test passes unchanged, and the OpenAPI spec is unchanged (the 404 responses the guards gave are still documented where a roll, frame or version isn't found).
