# FF-208 The roll repository's folder moves in their own files

**Status:** to do · **Group:** 16. Internal improvements

## Why

After FF-206 and FF-207, what still makes the filesystem roll repository long is two blocks of rename-and-roll-back code that aren't about the repository's interface. A reader should see the port's methods, each short enough to read without scrolling.

## What

Moving version folders when a frame's number or a version's kind changes, and moving roll folders in a batch through temporary names with rollback, each go into their own file as plain functions. The small filesystem helpers at the bottom of the repository go into one file they share. Nothing changes in behaviour. _(Recommendation R5c of the architecture review; the last of three tasks, after FF-207.)_

## Acceptance criteria

- [ ] `apps/backend/src/adapters/outbound/filesystem/move-version-folders.ts` holds the version folder moves: what `withChangedVersionPaths`, `versionFolderMoves` and the body of `#saveChanged` do now, as plain functions taking the `renameFolder` function the repository is given.
- [ ] `apps/backend/src/adapters/outbound/filesystem/renumber-roll-folders.ts` holds the batch's folder moves through temporary names and their rollback (the second half of `saveRenumberedBatch` now), the same way.
- [ ] `exists`, `isDirectory` and `removeIfEmpty` are in one small file in the same folder, used by the repository and the two new files.
- [ ] The repository file is about 300 lines: the port's methods and what only they use.
- [ ] A rollback that can't be completed still fails loudly, as now (D78).
- [ ] The filesystem adapter tests, the contract suite and the API tests pass unchanged, still driving the moves through the repository.

## Not in this task

- New tests for the moved functions on their own: the repository's tests already cover them at the right level.
- Changing how the moves or rollbacks work.
