# FF-240 Cancel stops a sync at once

**Status:** done · **Built in:** 17. Sync and backup

## Why

Pressing "Cancel" during a sync seems to do nothing. It only stops new files from starting, and the four uploads under way run to the end, which takes minutes with big scans. Nothing on screen changes until they finish.

## What

"Cancel" answers at once: it becomes "Stopping…", disabled, and the header reads "Stopping…", until the sync has stopped. The service cuts off the uploads under way, so it stops within a second or two. A file cut off part-way never reaches the bucket, and the next sync sends it, carrying on from the rest (FF-239).

## Acceptance criteria

- [x] Pressing "Cancel", in Settings or the header's panel, changes it straight away to "Stopping…", disabled. The progress line stays as it was, and the header reads "Stopping…", until the sync has stopped.
- [x] Once it has, Settings and the panel say "Sync stopped. The next sync carries on where this one left off." as a status, not an alert, and the header goes back to the last finished sync. A sync that fails still says "Sync didn't finish. Nothing already backed up was lost. Try again."
- [x] Cancelling aborts the uploads under way, not only those still to start, so the sync stops within a couple of seconds, whatever the files' sizes.
- [x] A file whose upload was aborted isn't in the bucket and isn't counted as sent. The next sync sends it.
- [x] The bucket's sync record and manifest stay as they were.
- [x] `GET /api/sync` gives the state `stopping` from the moment the cancel is asked until the sync has stopped, so Settings, the panel and a page opened meanwhile all read "Stopping…". It's in the OpenAPI spec.

## What was built

- **Service:** `LibrarySync.cancel()` sets `stopping` and aborts the job's signal, which each `putStream` now gets, so the uploads going are cut off; a worker whose upload was cut off just stops, and the run ends `cancelled`. Cancelling again while stopping is no failure, and `POST /api/sync` meanwhile follows the sync stopping. `SyncProgress.state` gained `stopping` in the contract and the OpenAPI spec.
- **Adapters:** `InMemoryPublishBucket.putStream` is cut off by its signal as a request is, putting nothing. The R2 adapter already passed the signal to its request.
- **Page:** `SyncControls` turns "Cancel" into "Stopping…", disabled, the moment it's pressed, and for a sync the service says is stopping; after a cancel it says "Sync stopped. The next sync carries on where this one left off." The header reads "Stopping…". `useSyncStatus` polls while stopping too.
- **Tests:** API (the uploads going are aborted, `stopping` until they've stopped, nothing in the bucket, the record and manifest unchanged; cancelling twice; starting while stopping), contract (a streamed put cut off part-way puts nothing, against the in-memory bucket and the fake R2), and web (Settings and the header).

## Not in this task

- Pausing and resuming: cancel, then sync again, carries on (FF-239).

## Notes

- **Needs first:** FF-239, so that cutting off uploads under way loses nothing.
