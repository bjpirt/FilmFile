# FF-236 Cloudflare in Settings

**Status:** to do · **Group:** 13. Sites

## Why

The Cloudflare account is the same for every site, and later for backing up and syncing, so it's set once in Settings, not on each site. Setting up R2 takes several steps in Cloudflare's dashboard, and Settings says what they are and whether the keys are in place.

## What

A "Cloudflare" section in Settings, after the FilmFile folder, holds the account ID (kept in `settings.json`, synced with the library) and says whether the keys are found in the `[filmfile]` profile of `~/.aws/credentials`. Under it, numbered steps say what to do in Cloudflare. A site's publish target loses its account ID and keeps only its bucket and address; publishing uses the account in Settings (D119).

## Acceptance criteria

- [ ] Settings has a "Cloudflare" section with an "Account ID" field and "Save". A valid ID (32 hexadecimal characters) is saved in `settings.json` as `cloudflareAccountId`; one that isn't valid says why under the field, in the service's words, and isn't saved. Emptying it and saving takes it away.
- [ ] Under the field, the section says "Keys: found in the [filmfile] profile of ~/.aws/credentials" when the profile has both keys, or "Keys: no [filmfile] profile in ~/.aws/credentials yet" when it doesn't (or the file is missing). The keys themselves are never shown, returned or logged; only whether both are there is checked, not whether Cloudflare accepts them.
- [ ] The section always shows these steps, the dashboard links opening in a new tab:
  1. "In the Cloudflare dashboard, open R2 and copy your Account ID into the field above."
  2. "Create a bucket for each site. Use it only for that site: files the site doesn't have are removed from it."
  3. "Under R2, Manage API tokens, create a token with Object Read & Write on those buckets."
  4. "Put its Access Key ID and Secret Access Key in ~/.aws/credentials:", followed by the `[filmfile]` profile as it should be written (`aws_access_key_id = …`, `aws_secret_access_key = …`).
  5. "Give each bucket a custom domain, and add a rewrite rule from / to /index.html."
  6. "Then set the bucket and address on each site's page."
- [ ] A site's publish target is `{ bucket, address }`: `PATCH /api/sites/{slug}` takes and gives that shape, and a site file written with an `accountId` is read with it ignored and drops it on the next save.
- [ ] Publishing, unpublishing and checking how the bucket stands use the account ID in Settings. Without one, `GET /api/sites/{slug}/published` answers `stands: "unknown"` with `check` saying "Set your Cloudflare account ID in Settings.", and publish and unpublish are refused (422) with the same message.
- [ ] `GET /api/settings` gives `cloudflareAccountId` (or null) and a read-only `cloudflareKeysFound`; `PATCH /api/settings` takes `cloudflareAccountId` (a string, or null). Both are in the OpenAPI spec.

## Not in this task

- The site page's Publish section (FF-234), which then has only "Bucket" and "Address".
- Typing the keys into FilmFile instead of `~/.aws/credentials` (FF-237).
- Checking the keys with Cloudflare from Settings: a site's "Check again" does that (FF-234).
- S3's settings (FF-200), and sync's bucket (FF-225), which uses this account ID.

## Notes

- **Decisions:** D119 (the account in `settings.json`, the keys per computer in `~/.aws/credentials`, one token for every bucket), amending D111 (the target was account ID, bucket and address) and D118 (the sync bucket's own details stay per computer).
- **Data:** `settings.json` gains `cloudflareAccountId: string | null` (absent in older files, read as null). It's the same account on every computer, so it syncs; a new computer types it once when it first downloads from the bucket (FF-227).
- **Keys found:** the `R2PublishBucket`'s credentials reader (FF-201) answers whether the profile has both keys, through the publish bucket port or a small port of its own, whichever is simpler when built; the answer is a boolean only.
- **Changes FF-201:** `PublishTarget` becomes `{ bucket, address }`; `SitePublishes` reads the account ID from the settings repository; `parsePublishTarget` loses the account ID rule, which moves to the settings' update.
- **Tests:** unit (the account ID rule), API (settings round trip, the keys-found flag with and without a credentials file, publishing without an account ID, an old site file with `accountId`), web (the Settings section's states and steps), and the publishing journey (FF-234) sets the account ID in Settings first.
