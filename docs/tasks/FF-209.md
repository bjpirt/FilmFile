# FF-209 The sites list reads the archive once

**Status:** to do · **Group:** 16. Internal improvements

## Why

Showing the sites page reads every roll, the settings and the events once for each site: five sites, five passes over the archive. The search for a selection's frames is pure logic wrapped round three reads, and those reads should happen once.

## What

Finding a selection's frames becomes a pure domain function, `findFrames`, given the rolls, the settings and the events' labels. `SearchFrames` loads those three and calls it, as before. `ListSites` loads them once and calls `findFrames` for each site, and no longer depends on another use case. Nothing changes in behaviour. _(Recommendation R6 of the architecture review, steps 1 and 2; the first of three tasks, before FF-210 and FF-211.)_

## Acceptance criteria

- [ ] `findFrames(selection, rolls, settings, eventLabels)` in `apps/backend/src/domain/selections/find-frames.ts` gives the same `FoundFrame` list `SearchFrames` gives now: the frames the rules find, hidden ones never, each marked if excluded by hand, with its roll's and event's labels, in shot order.
- [ ] `FoundFrame` is defined in the domain beside it.
- [ ] `findFrames` has unit tests in `find-frames.test.ts` for: a frame found by a rule, one excluded by hand, a hidden frame never found, a frame whose event has gone (no event label), and shot order across rolls.
- [ ] `SearchFrames.execute` reads the settings, every roll and every event, once each, and calls `findFrames`.
- [ ] `ListSites` is given the roll, settings, event and site repositories (not `SearchFrames`), reads the rolls, settings and events once whatever the number of sites, and calls `findFrames` for each.
- [ ] `GET /api/sites` answers as now; the sites, search, export and event API tests pass unchanged.

## Not in this task

- A site build's status (FF-210) and the equipment lookups in builds and exports (FF-211).
- An index (FF-122). See FF-211's note on when it's wanted.
- Moving the group labels out of `domain/sites/` (FF-222); `findFrames` imports them from where they are.

## Notes

- `SearchFrames` is `apps/backend/src/application/use-cases/selections/search-frames.ts`. `execute` (from about line 55) reads settings, `rolls.list` and `events.list` (into a `Map` of slug to `eventGroupLabel(event)`), then loops over every frame, building `frameFactsOf(roll, frame, resolveDetails([...]))`, matching with `matchSelection`, and sorting with `compareShotOrder`. Move the loop and sort; keep the reads.
- `FoundFrame` (about line 25) uses `FrameFacts` and `GroupLabel`; both are already in the domain.
- Suggested signature, taking what's read rather than the repositories:
  ```ts
  export function findFrames(
    selection: Selection,
    rolls: readonly Roll[],
    settings: Settings | undefined,
    eventLabels: ReadonlyMap<string, GroupLabel>,
  ): readonly FoundFrame[];
  ```
  Building `eventLabels` from the events can be a second small domain function used by both callers, or stay in each; three lines each is fine.
- `ListSites` is `apps/backend/src/application/use-cases/sites/list-sites.ts`, wired in `apps/backend/src/composition/use-cases-for.ts` (about line 165, `new ListSites(sites, searchFrames)`).
- Other users of `SearchFrames` (site builds, exports, events, the search route) are unchanged by this task.
