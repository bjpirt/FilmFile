# FF-155 Frame and version folders named by number and kind

**Status:** done · **Built in:** 8. Library on disk

## Why

In Finder, a roll's frames and versions should be recognizable without opening `roll.json`. Naming their folders by frame number and version kind makes the library readable while IDs keep each name unique.

## What

Store each version at `frames/<frame number>-<frame ID>/<kind>-<version ID>/<original name>`, using the last 8 characters of each ULID. Rename the frame folder when its number changes and the version folder when its kind changes; keep the version's relative path in `roll.json` in step with each move (D69). This task supports only the new layout; it does not migrate or support ID-only frame/version folders.

## Acceptance criteria

- [x] A frame with a version has a folder named `frames/<cleaned frame number>-<frame ID>/`, or `frames/unnumbered-<frame ID>/` when its number is null. The ID is the last 8 characters of its ULID.
- [x] A frame-number label keeps ASCII letters, digits and hyphens; each other character becomes `_`. A leading hyphen is prefixed with `_`. For example, `14-15` stays `14-15`, `12/13` becomes `12_13`, `.12` becomes `_12`, and `-12` becomes `_-12`.
- [x] An empty frame has no physical folder; its folder is created when its first version is stored.
- [x] A version folder is named `scan-<ID>`, `raw-scan-<ID>` or `final-<ID>`, using the last 8 characters of its ULID. Its files and sidecars keep their original names.
- [x] Changing a frame's number renames its frame folder; changing a version's kind renames its version folder. The corresponding `roll.json` paths are saved with the metadata change, and no file contents or names change.
- [x] Renumbering multiple frames in one roll, including swapping their numbers, renames all affected folders without collisions.
- [x] A missing source folder for a frame/version that has files, or an occupied destination folder, fails the save without overwriting anything or changing `roll.json`. A frame with no versions needs no source folder.
- [x] If an ordinary filesystem or metadata-save failure happens after a move, the service makes a best-effort rollback. It reports failure if rollback is incomplete; crash recovery is covered by FF-156.
- [x] Creating, reading originals and thumbnails, and deleting frames or versions work with the new paths. Version responses expose the original basename as `fileName`, never the filesystem path; browser journeys have no visible change.

## Not in this task

- Migrating or supporting archives with ID-only frame/version folders; this pre-release layout has no backwards-compatibility guarantee.
- Recovering a rename interrupted by a process stop or incomplete rollback (FF-156).
- Refreshing NegPy links automatically during a rename; they are rebuilt the next time the user chooses "Open in NegPy" (FF-112).
- Renaming original files, which keep their original names.

## Notes

- D69 replaces D17 and D58. D79–D83 record the label rule, new-layout-only scope, filesystem failure behavior, NegPy refresh timing and path-free version DTO. `roll.json` remains the source of each version's relative file path; the API exposes only its basename as `fileName`.
- Frame folders are lazy because a frame can exist without versions. New version uploads create the frame and version folders together.
- A rename changes paths, so backup and sync see the files as new; moving raw scans can trigger another Glacier minimum-storage charge. Frames are mostly renumbered before their raws are added.
- Tests: filesystem, repository contract and API tests cover new paths, cleaning, frame/kind changes, swaps, missing folders and collisions. Existing browser journeys remain unchanged.

## What was built

Filesystem uploads store versions in `frames/<number>-<frame ID>/<kind>-<version ID>/`. Frame-number and version-kind saves move the affected version folders, update every `roll.json` path in the same save, preflight missing sources and occupied destinations, and attempt rollback after ordinary failures. Empty frames remain metadata-only until their first version. The holding area follows the labeled paths for frame and version deletion. The API returns the original basename as `fileName`, not the stored path, so the web UI can keep labeling versions without exposing the archive layout.

Tests cover path cleaning, upload layout, frame renumbering and swaps, kind changes, path persistence, missing or occupied folders, rollback, deletion and path-free API responses. The existing eight browser journeys pass unchanged.
