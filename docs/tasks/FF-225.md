# FF-225 Back up the library to a bucket

**Status:** to do · **Group:** 17. Sync and backup

## Why

A copy of the whole library somewhere other than this computer, made in one click, so a lost or broken disk loses nothing. It's also the first half of syncing between computers.

## What

A "Sync" section in Settings takes a Cloudflare R2 bucket, kept on this computer only, and this computer's name. "Sync" uploads `Library/` and `settings.json` to the bucket as a mirror of the folder, sending only what changed since the last sync, and records the sync in the bucket. The first sync claims an empty bucket for this library. Until another computer joins (FF-227), syncing only goes up.

## Acceptance criteria

- [ ] Settings has a "Sync" section with "Cloudflare account ID", "Bucket" and "This computer's name" (prefilled with the computer's name, without `.local`). They're saved on this computer only, not in `settings.json`. Until account ID and bucket are filled in it reads "Say which bucket to sync with." and "Sync" is disabled.
- [ ] Invalid fields say why under them and aren't saved, with the same rules as FF-201 for the account ID and bucket. The name is 1–60 characters.
- [ ] "Sync" on a library that has never synced, with an empty bucket, uploads every file under `Library/` plus `settings.json`, at the same paths. Progress reads "Uploading 12 of 340". When it's done it reads "Synced 16 Nov 2026, 14:02".
- [ ] Syncing again uploads only files that are new or have changed since the last sync. With nothing changed, it uploads nothing and still reads "Synced …" with the new time.
- [ ] A file whose folder was renamed (a renumbered frame or roll) is copied inside the bucket from its old path, not uploaded again, and its old path is removed.
- [ ] Files emptied from `deleted/` by hand are removed from the bucket. Before that, the sync says "This sync will also remove 3 files emptied from deleted/ from the backup." with "Sync" and "Cancel".
- [ ] A file that a `roll.json` lists but that is missing from the library is never removed from the bucket. The sync finishes and says "2 files listed in the library are missing on this computer. The backup still has them."
- [ ] A bucket that isn't empty and wasn't claimed by this library is refused: "That bucket has something else in it, so FilmFile won't sync with it." The same bucket claimed by another library: "That bucket belongs to another FilmFile library."
- [ ] A sync that fails or is cancelled part-way leaves the bucket's sync record as it was, and reads "Sync didn't finish. Nothing already backed up was lost. Try again." The next sync carries on, uploading only what's still missing.
- [ ] Failures say what to fix, with FF-201's messages for missing keys, refused keys, no such bucket and being offline, and "Couldn't sync." for anything else, with no internals.
- [ ] The API: `GET`/`PUT /api/sync/settings`, `POST /api/sync` (start, 202), `GET /api/sync` (status and progress), `DELETE /api/sync` (cancel). All are in the OpenAPI spec.

## Notes

- **Decisions:** D115, D117. The bucket mirrors the folder. `filmfile/sync.json` (archive ID, sync number, computer name and time) and `filmfile/manifest.json` (every file's path, size and SHA-256) are written last, conditionally on the record read at the start, so a sync cut short leaves the old record in force.
- **Order of a push:** new files (copies for renames), then JSON, then removals, then the manifest and sync record.
- **On this computer:** the bucket details, the name and the last sync (number and manifest) are kept in the per-computer settings folder (D52), never in the library. Size and modified time decide which files to hash again, so a sync doesn't read every raw.
- **Requests:** FF-201's SigV4 signing and `[filmfile]` credentials. Whichever task is built first builds them; the other reuses them. The bucket port gains get, copy and conditional put (`If-None-Match`, `If-Match`) here. Contract suite against the in-memory adapter and the local S3-speaking test server.
- **Security** (the `security-rules` skill): requests only to the account's R2 host, paths in the bucket built from library-relative paths through the safe-path helper, and a downloaded manifest parsed with Zod.
- **Tests:** unit (planning uploads, copies and removals from two manifests), contract (bucket adapters), API (each route, with the in-memory bucket), web (the Settings section's states), and a journey that sets a bucket, syncs, renumbers a frame and syncs again.
