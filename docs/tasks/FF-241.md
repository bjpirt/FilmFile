# FF-241 How far the first sync has got

**Status:** done · **Built in:** 17. Sync and backup

## Why

A first sync of a big library can take several runs over days. Each run shows only its own upload, it says nothing while it reads the library before uploading, and between runs the header reads "Not synced yet". There's no telling whether a backup is a tenth done or nine tenths.

## What

A sync says what it's doing while it gets ready, and estimates the time left. Until the first sync finishes, its progress counts the whole library, including what's already in the bucket. Between runs, the header and panel say how far it got, worked out from the bucket when FilmFile opens. Later syncs, usually small, count only their own upload.

## Acceptance criteria

- [x] While a sync reads the library before uploading, it reads "Checking the library… 1,200 of 2,340 files", counted as files are hashed (files the hash cache already knows count at once). Then, while it lists the bucket, "Checking the bucket…". The header reads "Checking…". "Cancel" works throughout.
- [x] While the first sync uploads, or a run carrying it on, it reads "Backed up 13 GB of 34 GB (1,212 of 2,340 files)", counting what the bucket already had, and the header reads "Syncing 38%" for the whole library.
- [x] Later syncs read as now: "Uploading 1.2 GB of 3 GB (12 of 34 files)", and the header's percentage is of that upload.
- [x] Once a minute of uploading has been timed, the time left shows below: "About 2 h left", "About 5 min left", "Less than a minute left", from the speed over roughly the last minute. Before that, no estimate shows.
- [x] When FilmFile opens and this computer has never finished a sync, the service lists the bucket once, in the background. A bucket claimed by this library with no manifest (a first sync started but not finished) gives "First sync 38% done" in the header. The panel and Settings read "The first sync didn't finish: 13 GB of 34 GB backed up. Sync carries on from there."
- [x] Until that listing answers, if it can't reach the bucket, or for an empty bucket, the header reads "Not synced yet", as now.
- [x] The figure counts library files that are in the bucket at the same path and size, without hashing anything. The sync itself still checks MD5s before skipping a file (FF-239).
- [x] A first sync that stops (cancelled or failed) updates the figure from its own count, without listing the bucket again.
- [x] Once a first sync finishes, all of this goes: the header reads "Synced just now", and later syncs read as now.
- [x] `GET /api/sync` gives the phase (`checking-library`, `checking-bucket`, `uploading`), whether the run is the first sync, the whole library's bytes and files with how much is backed up, the seconds left or null, and between runs the first sync's figures or null. All are in the OpenAPI spec.

## What was built

- **Domain** (`domain/sync/`): `secondsLeft` (the speed since the newest sample at least a minute old), `BackupFigure` and `firstSyncFigure` (the library's files in a listing at the same path and size), and `bucketKeys`.
- **Port and adapters:** `LibraryFiles.describe` takes a `CheckingWatch` (told how many files are checked, of how many; stops on its signal), and `LibraryFiles.sizes` gives sizes without reading.
- **Use cases:** `LibrarySync`'s progress has `phase` (`checking-library`, `checking-bucket`, `uploading`), `filesChecked` and `filesToCheck`, `first`, `library` (the whole library's figure, for a first sync) and `secondsLeft`, worked out from samples taken as each file arrives. `FirstSyncFigures` keeps the figure between runs: it lists the bucket once in the background the first time it's asked (not while a sync runs), and a sync that stops sets it from its own count. `GET /api/sync` gained `firstSync`.
- **Page** (`apps/web/src/sync/`): `progressWords` (checking, backed up, uploading), `timeLeftText`, and the header's "Checking…", "Syncing 38%" of the whole library, and "First sync 38% done"; Settings and the panel read "The first sync didn't finish: … Sync carries on from there."
- **Journey:** the backup journey stops its first sync part-way, reloads to see "First sync …% done", then carries on. The fake R2 can make library uploads to a bucket slow (`slowPuts`); a slow upload cut off stores nothing.
- **Tests:** unit (`seconds-left`, `backup-figure`, `time-left-text`), contract (checking progress, stopping, sizes), API (the phases, a first sync's figures and carrying one on, the figure between runs from its own count and from the bucket after a restart, nothing when the bucket can't be reached, is empty, or a sync has finished), and web (each wording).
- One difference from the plan: the claim and the manifest are read before the library is checked, so a bucket that isn't this library's is refused before any hashing. They're quick, and show as "Checking the library…" with no count yet.

## Not in this task

- Speed limits, and pausing (cancel and sync again carries on, FF-239).

## Notes

- **Needs first:** FF-239 (checking the bucket before uploading), and FF-240 ("Stopping…" and the stopped message, which these sit beside).
- **First sync:** this computer has no last sync, and the bucket has no `filmfile/manifest.json`. During a run, "already backed up" is what FF-239's check found in the bucket.
- **Time left:** bytes sent over a moving window of about a minute, so one big file finishing doesn't swing it. It's rounded to minutes under an hour and to hours above.
- **On opening:** the service starts the listing once, when sync is ready and this computer has never finished a sync. The library's sizes come from listing its files (no reading). The answer is kept in memory with the service.
- **Tests:** unit (the time left from samples, and its wording at each rounding; the first sync's figure from a listing and the library), API (the phases; whole-library figures during a first sync; the figure between runs; an unreachable bucket), web (each wording in Settings, the panel and the header), and the backup journey extended: cancel a first sync part-way, reload, and see "First sync … done".
