# FF-106 Change a roll's number

**Status:** done · **Built in:** Roll numbers · **Was:** U25

## Why

A roll's number is only a guess until its negatives are filed: a wrong year, or a roll that should come before another, is put right by hand, and no two rolls may ever share a number.

## What

Edit details has a Roll number field, the first, like New roll's; changing it renames the roll's folder to match (`2026-009-Q2P7RM4K`, FF-151). No two rolls can have the same number: a roll's number changes only through the roll repository's `saveRenumbered`, which refuses a number another roll has (D70). Refusing a filed roll's number change is FF-107's. *(From 1.3.15, 1.4.3 and 1c.2.)*

## Acceptance criteria

The page:

- [x] Edit details has a "Roll number" field as its first, with the required star, the placeholder `2026-014` and the numbers font, as on New roll, filled with the roll's number.
- [x] A number that isn't `YYYY-NNN` is refused before anything is sent: "Enter a roll number like 2026-014: the year it was shot, then three digits."
- [x] A number another roll has is refused: "Roll 2026-009 already exists.", and nothing is saved.
- [x] Saving a changed number shows it at once, without reloading, in the roll's heading and breadcrumb, on the rolls page (in its new place in the order), on its frames' pages ("Roll 2026-009 / Frame 12") and on event pages.
- [x] The roll's address and links to it and its frames don't change, as they use its ID.
- [x] The number is sent only when it was changed: an untouched or restored number isn't sent, so saving the name or notes never depends on it.
- [x] A number whose year isn't the year shot is saved as it is, with no warning; so is changing the date shot without the number.
- [x] Renumbering a roll that has raw scans asks nothing and warns of nothing.
- [x] A change refused because the roll changed (409) says so ("The roll changed since you opened it. Reload the page.") and changes nothing.

The API:

- [x] `PATCH /api/rolls/{rollId}` takes `roll`, a well-formed number (`YYYY-NNN`): it changes the roll's number, keeps its ID, and answers with the roll and its new ETag; a malformed number is a 422 with an issue on `roll`.
- [x] A number another roll has is a 422 with an issue on `roll` ("is already used by another roll"), not a 409, which stays for "changed since it was read".
- [x] The roll repository refuses, atomically, giving a roll another roll's number, when creating one or changing a number with `saveRenumbered`; two requests can never both take a number. `save` and `change` never change a number, and throw if asked to.
- [x] The roll's folder on disk is renamed to `<new number>-<ID>` (FF-151), moving to the new number's year; the rolls list is in the new order.
- [x] A rolls page opened before the change still opens the roll by its ID.

## What was built

**The repository.** `RollRepository.saveRenumbered(ctx, roll, expectedVersion)` changes a number: under the roll's turn and then the years' turn it checks no other roll has the number (an unreadable roll's folder named for it counts), moves the roll's folder (FF-151's rename, now only here) and writes `roll.json` in it, returning `AlreadyExists` if the number is taken. The in-memory repository does the same under a lock of its own. `save` and `change` throw if a roll's number differs from what's stored.

**The use case and API.** `UpdateRoll` takes `roll`, checks its form (`parseRollNumber`) and saves through `saveRenumbered`, answering a taken number with a validation failure on `roll` ("is already used by another roll"), which the route sends as a 422. `updateRollRequest` takes `roll`; the OpenAPI spec and client are regenerated.

**The page.** `EditDetailsPanel` has "Roll number" first, checks its form before saving ("Enter a roll number like 2026-014: …"), and `saveDetails` in `roll-page.tsx` sends it only when it changed and says "Roll 2026-009 already exists." for a 422 on `roll`. Saving invalidates the rolls queries, so the heading, breadcrumb, rolls page, frame pages and event pages show the new number.

**Tests.** The contract suite covers `saveRenumbered` (renumbering, a taken number, the roll's own number, a stale version, a missing roll, two rolls taking one number at once, and `save` refusing a number change); the filesystem tests were moved to `saveRenumbered` (the swap goes by way of a spare number, and `change` refuses a number change); use case tests; API tests (renaming the folder, the list order, the 422s); page tests; and the "Catalogue a roll" journey changes a roll's number, reloads and finds it on the rolls page.

## Not in this task

- Refusing to change a filed roll's number, and showing it as not changeable (FF-107).
- Numbering many rolls at once, and swapping numbers through the API (FF-108).
- Warning when the number's year differs from the year shot.

## Notes

- Needs FF-151 (the folder naming and renaming).
- Decision D70. A number is changed only by the port's new `saveRenumbered`, which can fail with `AlreadyExists` (checked under a lock with the folder rename); `save` and `change` keep their types, so no other use case was touched. Rolls can no longer swap numbers one save at a time: FF-151's swap test now goes by way of a spare number, and FF-108's batch operation validates the final state instead.
- The page checks the format itself before sending, so a 422 on `roll` from the service means the number is taken.
- The use case, `UpdateRoll`, takes `roll` as it takes the other details and always saves through `saveRenumbered`, turning a taken number into a validation failure on `roll`; the number's year doesn't have to match the date shot (D7's "year shot" is a convention for new rolls).
- Tests: see What was built.
