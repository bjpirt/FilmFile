# FF-109 Originals read-only

**Status:** done · **Built in:** 8. Library on disk · **Was:** U74

## Why

Other programs that reach my originals (NegPy through its links, a file manager) mustn't be able to overwrite them in place by mistake.

## What

Every image FilmFile stores as a version (a lab scan, a raw scan, a final) is made read-only on disk as it's stored, and the service makes every image already in the library read-only once, in the background, when it starts. Only the image files: never `roll.json` or other JSON, sidecars or recipes, or folders.

## Acceptance criteria

- [x] An image added as a version is read-only on disk once stored: its write permission is removed for everyone and its other permissions are kept (a 0644 file is 0444, a 0600 file 0400).
- [x] On starting, the service makes every version's image already in the library read-only, in the background: it reads each roll's `roll.json` for its versions' files, changes only those that aren't read-only already, and the service answers requests while it runs.
- [x] The pass is quiet: it logs one line when it finishes ("Made 1,204 originals read-only; 3 couldn't be changed") and nothing when there was nothing to do, and later starts find nothing to change.
- [x] A file that's missing, or whose permissions can't be changed (a drive or share that doesn't support them, such as exFAT), is skipped and counted; storing an image never fails because its permissions can't be changed.
- [x] `roll.json`, other JSON files, sidecars and recipes, folders, and the contents and times of files are never changed, and nothing in `deleted/` is touched.
- [x] Deleting a version, frame or roll (moving its folder into `deleted/`), renumbering frames and changing a version's kind (renaming folders, FF-155) still work with read-only images.
- [x] Rotating a frame, which never touches its files, still works.
- [x] Adding the same file again is refused as before (originals are never overwritten, 'wx').

## What was built

`BlobStore` gained `makeReadOnly` (`changed`, `already`, `missing` or `failed`); the filesystem adapter's `put` clears the write bits of each image it stores right after writing it (`mode & ~0o222`, never failing the upload), and `makeReadOnly` does the same for files stored before. `ProtectOriginals` (`application/use-cases/originals/`) goes through every roll's recorded versions and counts what it changed and what it couldn't; `localStartup` in `composition/compose-local.ts` runs it once in the background as the service starts (`main.ts` calls it after the service is listening) and logs one line only when there was something to say ("Made 1,204 originals read-only; 3 couldn't be changed."). Tests: the blob store contract and the filesystem adapter (modes kept, times and contents untouched, missing files, an overwrite still refused), the use case's counting, the startup pass over a real temporary library (JSON, sidecars and `deleted/` untouched, quiet the second time), an API check that an uploaded scan is read-only, and the existing delete, renumber and kind-change tests, which now run on read-only files.

## Not in this task

- Making the version folders read-only, or locking files so they can't be deleted or moved: a program with write access to a folder can still delete or move a read-only file, by design (D51's guard is against overwriting in place).
- A Settings action to run the pass again (the integrity check could, FF-125).
- Linking originals for NegPy (FF-112), which relies on this.

## Notes

- D96. The pass reads `roll.json` through the roll repository, not by walking folders, so only recorded versions' files are touched; it runs once per start, sequentially and yielding between files, holds no lock, and never writes `roll.json`.
- Applied through the `BlobStore` port: `put` stores the image and makes it read-only; the filesystem adapter does the `chmod` (clearing the write bits of the mode); the in-memory adapter just keeps write-once, and the contract suite checks a stored blob can't be written again for both.
- On Windows, clearing write permission sets the file's read-only attribute, which stops overwriting but not deleting; moving a folder into `deleted/` is unaffected.
- Tests: the filesystem blob store's mode after `put` (including a mode other than 0644), the startup pass over a temporary archive (changes only what's needed, skips what it can't, leaves JSON and `deleted/` alone, logs one line), moves into `deleted/` and kind changes with read-only files, and rotation.
