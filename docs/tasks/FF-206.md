# FF-206 One lock in the roll repository

**Status:** done · **Built in:** 16. Internal improvements

## Why

The roll repository is the hardest file in the backend to read, and part of that is three nested locks where one does the work. D77 already describes the design as one in-process lock; the code should say the same.

## What

Each roll repository keeps one lock, `#archive`, around every roll change (and, in the filesystem one, every read). The inner locks, which can never wait because they're only ever taken inside it, go, and the callbacks they wrapped are un-nested. The lock's comment says everything it guards, including the year folders the inner lock was for, and the class comments are corrected. Nothing changes in behaviour. _(Recommendation R5a of the architecture review; the first of three tasks slimming the repository, before FF-207 and FF-208.)_

## Acceptance criteria

- [x] `FilesystemRollRepository` has one lock, `#archive`; `#lock` (per roll) and `#years` are gone.
- [x] `InMemoryRollRepository` has one lock, also named `#archive` (now `#writes`); its `#lock` is gone.
- [x] Every operation that took an inner lock still runs inside `#archive`, as it did: `create`, `save`, `saveRenumbered`, `change` and `remove` in both, and `saveRenumberedBatch`.
- [x] Each `#archive` has a comment saying what it guards: roll reads and changes take turns, so a listing is consistent while a batch is checked and applied (D77), roll numbers stay unique, and (filesystem) a year folder isn't removed as a roll is put in it.
- [x] The filesystem class comment no longer says "writes to the same roll take turns"; it says every roll read and change takes turns, one at a time (D77).
- [x] The concurrency tests (`apps/backend/test/api/concurrency.test.ts`), the roll repository contract suite (including its concurrent cases), the filesystem adapter tests and the API tests pass unchanged. No test is added or changed.

## What was built

- `FilesystemRollRepository` has one lock, `#archive`, with a comment saying what it guards: a consistent listing while a batch is applied, a number checked and taken with no other roll taking it, and a year folder not removed as a roll is put in it. `#lock` and `#years` are gone, and `create`, `save`, `saveRenumbered`, `change` and `remove` are un-nested (`#move`'s comment now says "the archive's turn"). The class comment says every roll read and change takes its turn (D77).
- `InMemoryRollRepository` has one lock, `#archive` (it was `#writes`), with a comment, and `create`, `save`, `saveRenumbered`, `saveRenumberedBatch`, `change` and `remove` are un-nested. Its `list` and `get` stay without the lock.
- Checked first: every inner lock was taken inside the archive-wide one, in both. No test was added or changed; the existing suites pass.

## Not in this task

- Replacing `KeyedLock`, though each repository now uses it with one key: it's tested, and the site, event and settings repositories use it too.
- Taking the lock in the in-memory repository's `list` and `get`: its reads are synchronous, so they can't see a write half done.
- New tests: the inner locks could never wait, so there's no behaviour to newly prove; the existing concurrency tests are the proof.
- Moving the renumbering rules (FF-207) or the folder moves (FF-208).
- Changing what's locked or for how long.
