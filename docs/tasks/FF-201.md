# FF-201 Publish a site to Cloudflare

**Status:** to do · **Group:** 13. Sites

## Why

Putting a built site on the web, on Cloudflare, without other tools, and keeping it in step with the archive in one click. This task is the service's half; the page that drives it is FF-234.

## What

A site gets a publish target, a Cloudflare R2 bucket on its own domain (account ID, bucket and the address it's seen at). The service says whether what's in the bucket matches the built site, publishes (building first as needed, then uploading only what differs and removing what's gone, with progress and cancel) and unpublishes. The keys come from the `[filmfile]` profile in `~/.aws/credentials`, so FilmFile keeps no keys (D111). The bucket is the site's alone: a full domain per site, with no folder (a folder on a shared domain is FF-235). _(Split from FF-121; the page split out as FF-234.)_

## Acceptance criteria

- [ ] A site has an optional target, `publish: { accountId, bucket, address } | null`, saved with the site through the existing site update route and returned with it. A site file without it reads as `null`.
- [ ] A target that isn't valid is refused with a validation error naming the field, and nothing is saved: an account ID that isn't 32 hex characters, a bucket name R2 wouldn't take, an address that isn't an `https://` URL.
- [ ] `GET /api/sites/{slug}/published` says how the bucket stands, from a listing of the whole bucket, comparing it with the built site by path, size and MD5 (the local files hashed when asked): not published; or published, with the time of `index.html` in the bucket, and either up to date or how many files need updating. With no target set, a validation error; with the site not built, it says the site isn't built.
- [ ] `POST /api/sites/{slug}/publish` starts a publish and answers 202, followed with the same kind of status as a build (its phase, "making images" and then "uploading", the files done and the total). Asking again while one runs follows that one. It builds the site first when it isn't built or is out of date, as a build would, and stops with the build's own failure if that fails.
- [ ] Only files that are missing or differ are uploaded, four at a time, with no retries, and files in the bucket that the built site no longer has are removed. Publishing again with nothing changed uploads and removes nothing.
- [ ] Images go up first, then pages, CSS and script, then removals, so a cancel or failure part-way leaves the published pages working as they were.
- [ ] `DELETE /api/sites/{slug}/publish` cancels: no new uploads start, those in flight finish, the status ends "cancelled", and nothing uploaded is rolled back.
- [ ] Each file is sent with its content type. Images get `Cache-Control: public, max-age=31536000, immutable`; pages, CSS and script `public, max-age=300`. `site.json` is never uploaded.
- [ ] `DELETE /api/sites/{slug}/published` unpublishes: removes every file in the bucket, and nothing in another bucket. The status afterwards is "not published". It refuses, changing nothing, when nothing is published.
- [ ] Publish and unpublish are refused with a conflict while a build, publish or unpublish of the site is running, and a build is refused while a publish runs.
- [ ] Each failure is a distinct error with its message, and anything already uploaded stays:
  - "No [filmfile] profile in ~/.aws/credentials, so the site can't be published."
  - "Cloudflare refused the keys in the [filmfile] profile."
  - "There's no bucket photos-pirt in that Cloudflare account."
  - "Couldn't reach Cloudflare. Are you online?"
  - "Couldn't publish the site." for anything else, with no internals.
- [ ] The keys are never stored, logged, returned by the API or put in an error.
- [ ] All four routes are in the OpenAPI spec.

## Not in this task

- The page: the "Publish" section, its fields, messages and the confirmation (FF-234).
- A folder in the bucket, for a site on a domain shared with other things (FF-235).
- S3 (FF-200), which reuses this task's bucket port and signing with AWS's endpoint.
- Choosing a profile name, or a Settings section for publishing: the profile is always `[filmfile]` until someone needs two.
- Temporary session tokens (`aws_session_token`): R2's tokens don't use them.
- Retrying a failed upload, or uploading more than four at a time.
- Guarding against two sites using one bucket: the page says the bucket is the site's alone (FF-234).
- Setting up the bucket, its custom domain, and the rewrite rule that serves `/index.html` at `/`. The notes say how, by hand.
- Cloudflare Pages or Workers static assets (capped at 20,000 files free, 100,000 paid), and publishing automatically on a change (workflows, design §11).

## Notes

- **Why R2 (D111):** no limit on files (a site is about 5 files a photo), free downloads, $0.015/GB-month past 10 GB, and S3's API, which FF-200 shares. Every link in a built site names its `.html` file, so only `/` needs the rewrite rule.
- **Whole bucket:** the target has no folder, so removals and unpublish act on everything in the bucket: it must be a bucket used only for this site. The page says so and the confirmation names the bucket (FF-234).
- **Data:** the target is kept with the site in `Library/sites/<slug>.json`, synced, since a site goes to the same place from any computer. Only the keys are per computer (D52), and they stay in `~/.aws/credentials` (or `AWS_SHARED_CREDENTIALS_FILE`), read when publishing and never stored or sent to the browser. This updates D92, whose targets were per computer.
- **Requests:** our own `fetch` to `https://<accountId>.r2.cloudflarestorage.com`, signed with AWS Signature Version 4 (region `auto`, service `s3`) using `node:crypto`; no SDK (a few lines of our own will do). ListObjectsV2 (1,000 per page), PutObject, DeleteObjects (1,000 per request). R2's ETag for a single-part upload is the file's MD5. The credentials file is parsed by a few lines of our own.
- **Ports:** a `PublishBucket` port (list, put, delete many), with an in-memory adapter and the R2 adapter, both run through one contract suite. The R2 adapter runs against a small local HTTP server speaking enough of S3's API, which also checks the signature. The use case reuses `SiteBuilds` to build first, and keeps one job per site like it.
- **Security** (the `security-rules` skill): outbound requests go only to the account's R2 host; the account ID and bucket are checked by Zod at the boundary; errors carry no internals; the address is only ever a link.
- **Tests:** unit (signing against AWS's published examples, the credentials file, the plan of uploads and removals), contract (both bucket adapters), and API (each route, with the in-memory bucket, including each failure).
- **Checking by hand against real R2:** make a bucket used only for the site and an R2 API token with read and write on it, put its access key ID and secret in `~/.aws/credentials` under `[filmfile]`, connect a custom domain to the bucket, and add a URL rewrite rule from `/` to `/index.html`.
