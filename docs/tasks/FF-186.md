# FF-186 The site's design as a template

**Status:** to do · **Group:** 13. Sites

## Why

Keeping what a site looks like apart from the code that builds it, so the design is files anyone can read and change, and later bring their own (FF-187).

## What

The built-in design moves out of the code into a template folder, `apps/backend/site-templates/filmfile/`: Liquid page templates, partials and `assets/`. The build gives the template a written, versioned set of data (the site, its cards, pages and frames, with every image's sizes) and writes what it renders; FilmFile still makes the images and keeps the site up to date. Sites look the same as before. _(From feedback on the first sites, FF-119 and FF-120; custom templates split into FF-187.)_

## Acceptance criteria

The template:

- [ ] `apps/backend/site-templates/filmfile/` holds `template.json` (its name, "FilmFile", and the data version it's written for, 1), `cards.liquid`, `group.liquid` (a roll's or event's page), `frame.liquid`, partials such as `_header.liquid`, and `assets/` (the stylesheet and script), copied into the built site as is.
- [ ] A site built with it has the same pages as before, the same text, links, images and structure; only whitespace may differ, so sites built before go "Out of date" once.
- [ ] No page, stylesheet or script text is left in `domain/sites/`; the domain builds only the data.

The data:

- [ ] What each page is given is one Zod schema, version 1 (the site's name, the view and menu, the cards, a roll's or event's page with its frames, a frame page with its place, neighbours, filmstrip and caption, and every image's path and width for `srcset`), with relative links worked out by FilmFile; a test checks the data given to every page against it.
- [ ] `docs/site-templates.md` describes each page's data with an example, and a JSON Schema generated from the Zod schema sits beside it and is checked in as `pnpm generate` keeps the OpenAPI spec.

Rendering:

- [ ] Rendering is a `SiteRenderer` port: the data in, the files out; a Liquid adapter (liquidjs) renders a template folder, and an in-memory one serves use-case tests; one contract suite runs against both.
- [ ] Every output is escaped unless a template writes `| raw`: a frame titled `<b>Harbour</b>` shows those characters on the page.
- [ ] A template can only include files from its own folder: no absolute paths, `..` or links out (tested).
- [ ] Image sizes stay FilmFile's: 240, 480, 960 and 1600; the template picks among them, and images, their hashed names and the up-to-date check don't depend on the template.

Up to date:

- [ ] `site.json` records a hash of the template's files; changing any of them makes the site "Out of date", and building again rewrites only the pages and assets that changed, never an image.
- [ ] Building a site that's up to date still changes nothing (FF-120).

## Not in this task

- A template of your own, and choosing one for a site (FF-187).
- Template options (colours, fonts) set on a site's page, and image sizes chosen by a template.

## Notes

- New dependency: `liquidjs`, for a safe, known template language with escaping by default and no code run in the service (no dependencies of its own); checked as `security-rules` says. D106 records the choices.
- The adapter is given the template folder's path by the composition; the backend build and the desktop app's package copy `site-templates/`.
- The domain's page functions (`renderSitePage` and the rest) become data builders; the escaping and markup move into the templates.
- Needs FF-183 and FF-184 first, so the template covers the real pages; do last in group 13 before FF-187.
- Tests: the data builders (unit), the renderer contract suite (escaping, includes kept inside the folder, missing page reported), the build (template hash, out of date, images untouched) and the existing `build-site.e2e.ts`, unchanged, passing.
