# FF-204 Let browsers cache thumbnails

**Status:** to do · **Group:** 16. Internal improvements

## Why

Every visit to a roll fetches every thumbnail again, and each fetch looks up the roll and reads a cached image from disk. A thumbnail's address names its bytes (the version is write-once, and the size and turn are in the address), so the browser can keep it.

## What

The thumbnail route tells the browser to keep each thumbnail for a year and not ask again: `Cache-Control: private, max-age=31536000, immutable`. That's only true while the way thumbnails are made stays the same, so a rule goes with it: a change to how thumbnails are made changes their address and the service's cached files' names, in the same task (D114). _(Recommendation R3 of the architecture review.)_

## Acceptance criteria

- [ ] `GET /api/rolls/{rollId}/frames/{frameId}/versions/{versionId}/thumbnail` answers 200 with `Cache-Control: private, max-age=31536000, immutable`, at both sizes and every turn.
- [ ] A thumbnail that isn't found (404) or a request that's refused (422 for a bad size or turn, 403 for a wrong Host or Origin) carries no `Cache-Control` header of this kind.
- [ ] The other security headers are on the thumbnail's response as on every other.
- [ ] The route's OpenAPI definition describes the header on its 200 response, and `pnpm generate` is run.

## Not in this task

- Caching originals (`…/versions/{versionId}/file`): they can be 200 MB and are fetched rarely twice.
- Caching anything else: rolls, frames and lists change.
- A format number in the address now: it's added by the first task that changes how thumbnails are made (D114), not ahead of it.
- Keeping the desktop app's cache across launches: the app starts its service on a new port each launch and the browser keeps its cache per origin, so the cache lasts only until the app quits. Accepted; across launches a fetch is cheap since FF-202. In a browser on `pnpm start`, whose port is fixed, it lasts.
- A journey or by-hand check that the browser obeys the header: that's the browser's job.

## Notes

- D114, and `docs/design.md` section 13.8, already say thumbnails are kept for a year and what a change to how they're made must do.
- Read the `security-rules` skill before touching the route.
- The handler is near the end of `apps/backend/src/adapters/inbound/http/routes/rolls.ts` (about line 786): `useCases.getThumbnail.execute`, then `c.body(new Uint8Array(thumbnail.value), 200, { 'Content-Type': 'image/webp' })`. Add `'Cache-Control'` to that header object only. The route definition is at about line 438 (`getThumbnail`, its 200 built with `image('image/webp', …)`); describe the header there. If FF-217 is done first, the route is in `routes/frame-versions.ts`.
- Why the address names the bytes: `apps/web/src/rolls/thumbnail-url.ts` builds `…/versions/{versionId}/thumbnail?size=small|large[&rotate=90|180|270]` from a version the page has just read from the API (it's used by `thumbnail.tsx`, `roll-card.tsx`, `roll-table.tsx` and `events/event-card.tsx`, each from a frame in an API response). Versions are write-once and IDs are ULIDs, never reused.
- What D114 guards against: the service caches thumbnails in the OS cache folder named `<sha256>-<size>[-<turn>].webp` (`apps/backend/src/adapters/outbound/sharp/sharp-preview-provider.ts`, about line 33), with nothing for how they were made. A change to that code (for example a fix to how a scan's orientation is read, like `9ab8b13`'s fix to exports) must add something such as `&v=2` to the address in `thumbnail-url.ts` (accepted by the route's query schema) and to the cached files' names, so neither cache serves the old image.
- `private` because the service is one person's and local.
- Tests: API tests in `apps/backend/test/api/` (beside the existing thumbnail tests): the header on a found thumbnail, small and large, turned and not; none on a 404, a 422 and a 403.
