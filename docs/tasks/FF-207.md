# FF-207 Renumbering rules in the domain

**Status:** to do · **Group:** 16. Internal improvements

## Why

The rules for renumbering rolls are written out in full in both roll repositories, about 110 lines each, with the same messages. They're rules about rolls, not files, and the two copies have already drifted: they treat unreadable rolls differently.

## What

One pure domain function, `planRollRenumbering`, checks a batch renumbering against the archive as it is now and gives the rolls whose numbers really change, or why it can't be applied. A second small function holds the rule that a filed roll's number can't be changed. Both repositories call them inside their lock, and their `saveRenumberedBatch` becomes: take the lock, read the current rolls, plan, apply. Nothing changes in behaviour, and no API test changes. _(Recommendation R5b of the architecture review; after FF-206, before FF-208.)_

## Acceptance criteria

- [ ] `apps/backend/src/domain/rolls/plan-roll-renumbering.ts` exports `planRollRenumbering`, a pure function (no I/O), with a TSDoc comment.
- [ ] It refuses with the same error kinds, paths and messages as the filesystem repository today, checked in the same order:
  1. the snapshot names a roll twice: validation failed, `snapshot`, "contains a duplicate roll";
  2. a roll in the snapshot is missing or its version has changed: concurrency conflict for that roll;
  3. a roll has been added since the snapshot: concurrency conflict for that roll;
  4. the unreadable rolls differ from the snapshot's: concurrency conflict, id `unreadable`;
  5. the changes name a roll twice: validation failed, `changes`, "contains a duplicate roll";
  6. a change names a roll not in the archive or the snapshot: validation failed, `changes`, "includes an unknown roll";
  7. a change gives a filed roll another number: validation failed, `roll`, "A filed roll's number can't be changed.";
  8. the numbers after the changes aren't unique: validation failed, `changes`, "roll numbers must be unique";
  9. a number after the changes is held by an unreadable folder: validation failed, `changes`, "a roll number is used by an unreadable roll folder".
- [ ] Otherwise it gives the changes whose number really differs from the roll's current one (those the filesystem repository moves now, its `moving` list), in the order of `current` so the folder moves keep today's order.
- [ ] A unit test, `plan-roll-renumbering.test.ts`, table-style: one case for each refusal (including an unreadable-list mismatch and a number held by an unreadable folder), the happy path, and the order of the result.
- [ ] The check that an unreadable folder holds a number (`namedFor`, now in the filesystem repository) is the domain function `folderHoldsNumber(folder, roll)` in `domain/rolls/folder-holds-number.ts`, with its comment, used by the plan and by the filesystem repository's single-roll number check.
- [ ] A domain predicate, `mayChangeRollNumber(roll)`, says whether a roll's number may be changed (true unless it's filed). The message "A filed roll's number can't be changed." is one exported constant. The plan and `saveRenumbered` in both repositories use both, so the message is written once.
- [ ] Both repositories' `saveRenumberedBatch` call `planRollRenumbering` inside their lock and only apply its result. The in-memory one is about 20 lines.
- [ ] The two repositories now treat unreadable rolls the same way, the filesystem one's way. If that changes what the in-memory one does in a contract test, the test is fixed to the filesystem's behaviour and the task says so.
- [ ] The roll repository contract suite gets no new case; unreadable behaviour is covered by the unit test and the existing filesystem adapter test.
- [ ] The roll repository contract suite, the filesystem adapter tests and the API tests pass, the API tests unchanged.
