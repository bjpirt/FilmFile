# FF-203 Report failures in background work

**Status:** done · **Built in:** 16. Internal improvements

## Why

When a site build fails, or a frame can't be made in an export, the page rightly says only that it failed (or lists the frame in `skipped.txt`), but the error itself is dropped, so there's nothing to find out why from. CLAUDE.md says never swallow errors, and four places do.

## What

A small outbound port, `ErrorReporter`, takes an unexpected failure, with a few words saying what was being done, to the service's error output, as a request's errors go now. Site builds, exports (each frame that can't be made, and an export to a folder that stops) and the startup step that makes originals read-only report what they catch. What the page shows doesn't change. While here, an export to a folder cancels with an `AbortController`, as a site build does, and `docs/design.md` says the two background runners are job runners, not use cases. _(Recommendation R2 of the architecture review; D113.)_

## Acceptance criteria

- [x] A site build that throws ends `failed`, as now, and reports once, "Couldn't build site iceland" (the site's slug) with the error.
- [x] In an export, zip or folder, a frame whose image can't be made for an unexpected reason is still left out and listed in `skipped.txt` with "its image couldn't be made", as now, and is reported, "Couldn't make frame 12 of roll 2026-014" (as `skipped.txt` names it) with the error: one report for each such frame.
- [x] A frame left out for an expected reason (hidden, no scan, no longer there) isn't reported.
- [x] An export to a folder that stops altogether (a file can't be written) ends `failed`, as now, and reports once, "Couldn't finish an export to a folder" with the error.
- [x] A build or an export that's cancelled, or that fails in an expected way (a `Result` error such as a site folder in the way), reports nothing.
- [x] When making originals read-only at startup throws, it reports "Couldn't make originals read-only" with the error, and the service still starts (`localStartup` never throws). An archive with nothing in it still reports and says nothing.
- [x] Running the service, a report is written to its error output: the words, then the error with its stack.
- [x] Nothing more reaches the page or the API: the build and export statuses, `skipped.txt` and the error responses are as now.
- [x] Cancelling an export to a folder works as now (it stops after the file in progress, keeps what's written and says it was cancelled), now through an `AbortController`.
- [x] `docs/design.md` section 13.4's port table has `ErrorReporter`, and section 13.5 says `SiteBuilds` and `FolderExports` are job runners: they keep jobs in memory and offer `start`, `status` and `cancel`, not one `execute`.

## What was built

- The port `apps/backend/src/application/ports/error-reporter.ts` (`report(what, error)`), with `ConsoleErrorReporter` (`adapters/outbound/node/`, `console.error(`${what}:`, error)`) and `InMemoryErrorReporter` (`adapters/outbound/memory/`, keeping each `{ what, error }` in `reported`). `errors` is in `Adapters`; `composeLocal` gives the console one, `composeInMemory` the in-memory one.
- `SiteBuilds` reports "Couldn't build site <slug>"; `MakeQuickExport.entries` reports "Couldn't make frame 12 of roll 2026-014" for each frame it can't make for a reason it doesn't give, and still lists it in `skipped.txt`; `FolderExports` reports "Couldn't finish an export to a folder" and cancels through an `AbortController`; `localStartup` reports "Couldn't make originals read-only".
- `localStartup`'s reporter is a third argument that defaults to the console one, rather than `main.ts` passing it, since `main.ts` may import only the composition (the boundaries rules).
- `docs/design.md`: `ErrorReporter` in section 13.4's table, and a paragraph in 13.5 on the job runners.
- Tests: `apps/backend/test/api/reported-failures.test.ts`, through `composeInMemory` with a broken renderer, a folder that refuses writes and one held mid-write: a failed site build, frames that break in a zip and a folder export, a folder export that stops, and nothing reported for a working build, a hidden frame or a cancelled export. `local-startup.test.ts`: a `roll.json` that's a folder makes listing throw, and it's reported once. A contract suite (`error-reporter-contract.ts`) run against both adapters, and a test beside each.

## Not in this task

- A log file, so the packaged app's errors can be found: FF-224. Until then, a packaged app's error output goes nowhere a person can see; run from source, it's the terminal.
- Telling the page more, such as an ID to quote: the page says only that it failed, as now.
- Sending background reports to `composeLocal`'s `reportError`, which stays for request errors only.
- A correlation ID on background reports: nothing shows one, so nothing needs one.
- A shared job framework for the two runners: two is too few to abstract from.
- Reporting from anywhere else: the HTTP adapter's `errorHandler` already reports what a request throws.

## Notes

- The four silent catches:
  - `SiteBuilds.#run` in `apps/backend/src/application/use-cases/sites/site-builds.ts` (about line 187): `catch { update({ state: 'failed' }) }`. `BuildSite.execute` lets a failure in making an image throw (after discarding the half-made build), so the whole build fails and this is where it's reported.
  - `MakeQuickExport.entries` in `apps/backend/src/application/use-cases/exports/make-quick-export.ts` (about line 162): catches every error per frame; a `LeftOut` is expected, anything else becomes "its image couldn't be made". Report the latter, with `#describe`'s words. `entries` serves both zip downloads and folder exports.
  - `FolderExports.#run` in `apps/backend/src/application/use-cases/exports/folder-exports.ts` (about line 173): `catch { update({ state: 'failed' }) }`. With per-frame errors caught in `entries`, this is reached when the folder refuses a write.
  - `localStartup` in `apps/backend/src/composition/compose-local.ts` (about line 53): `catch {}` around `ProtectOriginals`.
- The port, `apps/backend/src/application/ports/error-reporter.ts`:
  ```ts
  /** Where an unexpected failure goes so it can be diagnosed: the log, never the client. */
  export interface ErrorReporter {
    /** `what` says what was being done, e.g. "Couldn't build site iceland". */
    report(what: string, error: unknown): void;
  }
  ```
- Adapters: `adapters/outbound/node/console-error-reporter.ts` (`console.error(`${what}:`, error)`, which prints the stack) and `adapters/outbound/memory/in-memory-error-reporter.ts` (keeps each `{ what, error }`, with a `reported` getter, for tests).
- Wiring: add `errors: ErrorReporter` to `Adapters` in `apps/backend/src/composition/use-cases-for.ts`, given to `SiteBuilds`, `FolderExports` and `MakeQuickExport`. `composeInMemory` gives the in-memory reporter by default (a test can pass its own through `overrides`, as with any adapter); `composeLocal` the console one. `localStartup` takes the reporter as a third argument, and `main.ts` passes the console one.
- `FolderExports` keeps `cancelled: boolean` on its job (about line 30). Replace it with `controller: AbortController` and check `controller.signal.aborted`, as `SiteBuilds` does (about lines 41 and 141). The cancel tests in `apps/backend/test/api/folder-exports.test.ts` pass unchanged.
- Tests first, through `composeInMemory` with an `ImageRenderer` that throws and an in-memory reporter: in `apps/backend/test/api/site-builds.test.ts` (failed, one report naming the site), `exports.test.ts` (a zip's `skipped.txt` as now, one report per frame), `folder-exports.test.ts` (done, a report per frame; and with a destination whose folder refuses a write, a small fake written in the test: failed, one report). Expected cases: a hidden frame and a cancelled job report nothing. Startup: in `apps/backend/test/composition/local-startup.test.ts`, an archive that makes `ProtectOriginals` throw (for example a `rolls` that's a file, not a folder) reports once and resolves.
- Contract suite: every port has one (`testing-conventions`). A short one: `report` takes any value as the error without throwing. Run it against both adapters; the in-memory one's `reported` is checked in its own test.
- `security-rules`: errors never reach the client; only the log.
