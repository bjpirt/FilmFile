# FF-244 Publish a release

**Status:** done · **Built in:** 10. Desktop app

## Why

Merging a release's pull request publishes it: the app built and checked the same way each time, rather than by hand on my Mac, with notes that say what changed and how to open it.

## What

A "Release" workflow runs when a push to `main` changes the root `package.json` or `CHANGELOG.md`, or when it's run by hand. If that version hasn't been released (there's no `v` tag for it), it builds the app again from that commit and checks it through a reusable `package.yml`, and only if that passes publishes the GitHub release "FilmFile 0.4.0": the disk image, `SHA256SUMS`, build provenance for each file, and notes from the changelog entry with a note on opening an app that isn't signed. It runs only on `main`, never on pull requests. At first that's the Apple-silicon Mac's disk image; Intel (FF-161), Windows and Linux (FF-197, FF-198) add their rows to `package.yml`. _(Split from FF-195.)_

## Acceptance criteria

Starting:

- [x] A push to `main` that changes the root `package.json` or `CHANGELOG.md` starts "Release" (the first release, `0.1.0`, changes only `CHANGELOG.md`, FF-243). Pull requests never start it.
- [x] Actions › "Release" › "Run workflow", on `main`, starts it for the version in `package.json`, so a release that failed is tried again once it's fixed.
- [x] If the tag `v<version>` already exists, the run succeeds having done nothing, its summary saying "0.4.0 is already released:" with the release's link.
- [x] If `CHANGELOG.md` has no entry for the version, the run fails before building anything, saying "CHANGELOG.md has no entry for 0.4.0. Prepare releases with pnpm release."
- [x] Only one release runs at a time (a concurrency group, never cancelling one under way).

Building:

- [x] It builds the app from the commit that started it, through `.github/workflows/package.yml`, and runs the packaged-app journey on it. If that fails, nothing is released. It doesn't reuse apps built on the pull request.
- [x] `ci.yml` calls `package.yml` in place of its `desktop-app` job, so pull requests still build and check the Apple-silicon app as now.

Publishing:

- [x] The release is made as a draft first, with every file and its provenance, then published as the latest release, which makes the tag `v0.4.0` on the commit it built. A run that fails part-way leaves at most a draft, which running again replaces; nothing half-made is public.
- [x] It's titled "FilmFile 0.4.0", a normal release (not a pre-release), set as latest.
- [x] Its notes are the version's `CHANGELOG.md` entry without its heading, then "### Installing": open the disk image and drag FilmFile to Applications; the app isn't signed yet, so the first time macOS won't open it: choose Done, then System Settings › Privacy & Security › Open Anyway; and check the download with `shasum -a 256 -c SHA256SUMS`. A unit test covers the notes.
- [x] It holds `FilmFile-0.4.0-mac-arm64.dmg` and `SHA256SUMS`, one line per file in `sha256sum`'s format, checkable with `shasum -a 256 -c SHA256SUMS`.
- [x] Each file has build provenance (`actions/attest-build-provenance`), so `gh attestation verify FilmFile-0.4.0-mac-arm64.dmg --repo bjpirt/FilmFile` passes.

Security:

- [x] Only the publishing job can write: `contents: write`, `id-token: write` and `attestations: write`. The other jobs read only, and no secret is used beyond `GITHUB_TOKEN`. Actions are pinned to commit SHAs.

## What was built

- `.github/workflows/release.yml`, "Release": _check_ (on `main` only; reads the version, looks for `v<version>` with `gh api`, and if it's new writes the notes with `node scripts/release-notes.ts` and keeps them as an artifact), _package_ (`package.yml` with `release: true`, which installs without the pnpm cache), and _publish_ (downloads the disk images and notes without checking out the repository, writes `SHA256SUMS`, attests every file, deletes a draft left by a failed run, makes the draft with `gh release create --draft --target <sha>`, then publishes it with `gh release edit --draft=false --latest`). Values reach shell steps through `env:`, never inline.
- `.github/workflows/package.yml`: CI's old `desktop-app` job, with a matrix of one row (`mac-arm64` on `macos-latest`), uploading `FilmFile-<platform>` artifacts. `ci.yml`'s `desktop-app` job calls it, so its check is now reported as `desktop-app / mac-arm64`, and the ruleset's required check changes with it.
- `scripts/release-notes.ts`, with `scripts/release/release-notes.ts` and their tests.
- The workflows only run on GitHub: the first release, 0.1.0, is their first full run.

## Not in this task

- Bumping the version and writing the changelog (FF-243).
- The Intel Mac's build (FF-161), and Windows and Linux (FF-197, FF-198): each adds its row to `package.yml`, and so to releases.
- Building every platform on a release's pull request: the release builds and checks again on `main` before publishing.
- Signing (FF-137, FF-199) and updates (FF-138). The Installing note goes when the app is signed.
- Running `pnpm verify` and the browser journeys again: the pull request's CI already has (the release checks only the packaged app).
